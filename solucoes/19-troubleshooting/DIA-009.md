# Gabarito DIA-009 — Caso 07: o rollout que não termina e o undo que não volta

> Consulte só depois de tentar. Enunciado: [trilhas/19-troubleshooting/exercicios/DIA-009.md](../../trilhas/19-troubleshooting/exercicios/DIA-009.md)

## Desafio sem pista — uma solução possível

Defeitos: (1) a imagem nova não existe (`ErrImagePull`), e o rollout para em `ProgressDeadlineExceeded` (60 s) — os
pods antigos continuam atendendo graças a `maxUnavailable: 0`; (2) `revisionHistoryLimit: 0` faz o Kubernetes apagar
os ReplicaSets antigos, então o `undo` não tem para onde voltar.

```bash
oc set image deployment/ac19-c7 web=registry.access.redhat.com/ubi9/httpd-24:latest -n ac19-casos
oc patch deployment ac19-c7 -n ac19-casos --type=merge -p '{"spec":{"revisionHistoryLimit":5}}'
oc rollout status deployment/ac19-c7 -n ac19-casos
oc set env deployment/ac19-c7 VERSAO=2 -n ac19-casos && oc rollout status deployment/ac19-c7 -n ac19-casos
oc rollout history deployment/ac19-c7 -n ac19-casos        # agora há revisões
oc get rs -n ac19-casos -l app=ac19-c7        # o RS da revisão anterior agora é guardado: o undo teria para onde voltar
```

## Diagnóstico controlado — explicação

O histórico do Deployment são os ReplicaSets antigos; limite zero significa não guardar nenhum.
