# Gabarito POD-012 — Requests, limits e classes de QoS

> Consulte só depois de tentar. Enunciado: [trilhas/04-pods/exercicios/POD-012.md](../../trilhas/04-pods/exercicios/POD-012.md)

## Desafio sem pista — uma solução possível

```bash
for nome in g2 b2; do
  LIM2='{"cpu":"20m","memory":"32Mi"}'; [ "$nome" = b2 ] && LIM2='{"cpu":"40m","memory":"32Mi"}'
  cat <<EOF | oc apply -n ac04-pods -f -
apiVersion: v1
kind: Pod
metadata: {name: ac04-qos-$nome, labels: {academy.openshift.dev/managed-by: academia}}
spec:
  restartPolicy: Never
  containers:
    - {name: a, image: registry.access.redhat.com/ubi9/httpd-24:latest, command: [sleep, "600"], resources: {requests: {cpu: 20m, memory: 32Mi}, limits: {cpu: 20m, memory: 32Mi}}}
    - {name: b, image: registry.access.redhat.com/ubi9/httpd-24:latest, command: [sleep, "600"], resources: {requests: {cpu: 20m, memory: 32Mi}, limits: $LIM2}}
EOF
done
oc get pod ac04-qos-g2 ac04-qos-b2 -n ac04-pods -o custom-columns=NOME:.metadata.name,QOS:.status.qosClass
```

No `b2`, só o `limits.cpu` do contêiner `b` difere do request — basta isso para virar `Burstable`.

## Diagnóstico controlado — explicação

O LimitRange recusa na admissão, antes de gravar. `max` vale por contêiner; ajuste o limit para ≤ 512Mi.
