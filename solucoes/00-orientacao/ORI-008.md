# Gabarito ORI-008 — Capacidade do SNO antes de praticar

> Consulte só depois de tentar. Enunciado: [trilhas/00-orientacao/exercicios/ORI-008.md](../../trilhas/00-orientacao/exercicios/ORI-008.md)

## Desafio sem pista — uma solução possível

```bash
oc adm top nodes --no-headers | awk '{print "uso_real_mem=" $5}'
oc describe node ocp-sno.ocp.example.lab | awk '/^Allocated resources:/,/^Events:/' | awk '$1=="memory" {print "requests_mem=" $3}'
oc get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded --no-headers 2>/dev/null | wc -l
oc get node ocp-sno.ocp.example.lab -o jsonpath='memory_pressure={.status.conditions[?(@.type=="MemoryPressure")].status}{"\n"}'
```

Decisão: pratica se uso real < 85%, requests < 90%, nenhum pod anormal recorrente e `MemoryPressure=False`.

## Diagnóstico controlado — explicação

Logo após o boot, `oc get apiservice v1beta1.metrics.k8s.io` pode mostrar `AVAILABLE=False` por alguns minutos; quando
passar a `True`, `oc adm top` volta a funcionar (hipótese a). Se persistir com o operador `monitoring` degradado,
registre e não tente corrigir mexendo em `openshift-monitoring`.

## Erros comuns

- Olhar só `oc adm top` e concluir que há espaço, ignorando os requests.
- Criar pods "para testar" a capacidade: no SNO isso compete com o control plane.
