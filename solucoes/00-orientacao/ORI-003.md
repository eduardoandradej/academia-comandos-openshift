# Gabarito ORI-003 — admin e developer existem? Conferir o provedor HTPasswd

> Consulte só depois de tentar. Enunciado: [trilhas/00-orientacao/exercicios/ORI-003.md](../../trilhas/00-orientacao/exercicios/ORI-003.md)

## Desafio sem pista — uma solução possível

```bash
oc get oauth cluster -o jsonpath='{range .spec.identityProviders[*]}{.name}{" "}{.type}{"\n"}{end}'
oc get user developer -o name 2>/dev/null || echo "developer ainda não fez login"
oc get identities -o custom-columns=IDENT:.metadata.name,USER:.user.name
oc get clusterrolebindings -o json | jq -r '.items[]
  | select(.roleRef.name=="cluster-admin" and any(.subjects[]?; .kind=="User" and .name=="admin"))
  | .metadata.name'
```

Interpretação: o provedor aparece como `homelab-users HTPasswd`; a identidade `homelab-users:developer` prova login
anterior; o nome do binding retornado é a evidência do `cluster-admin` de `admin` (o comando `oc adm policy
add-cluster-role-to-user` costuma gerar um binding com nome `cluster-admin-` seguido de sufixo).

## Diagnóstico controlado — explicação

A: sem `Identity` `homelab-users:developer`, não houve login concluído por esse provedor — o objeto `User` nasce no
primeiro login bem-sucedido. B: lista vazia significa que `spec.identityProviders` não tem entradas; a Academia não
configura isso automaticamente porque alterar o OAuth reinicia os pods de autenticação e pode bloquear o acesso.

## Erros comuns

- Usar `oc get secret homelab-users-htpasswd -n openshift-config -o yaml` "só para ver": expõe os hashes.
- Criar `new_admin`/`new_developer` agora: estraga o exercício de identidade do DO280.
