## Conceito

`metadata.ownerReferences` diz quem é o dono de um objeto (`kind`, `name`, `uid`). Quando o dono é apagado, o
**coletor de lixo** apaga os dependentes:

| `--cascade=` | Efeito ao apagar o dono |
|---|---|
| `background` (padrão) | apaga o dono já; os dependentes são removidos em seguida |
| `foreground` | o dono fica com `deletionTimestamp` até os dependentes sumirem |
| `orphan` | apaga só o dono; os dependentes ficam, sem `ownerReferences` |

O dono precisa estar no **mesmo namespace** (ou ser de cluster) e a referência usa o `uid` — por isso um objeto
recriado com o mesmo nome não "herda" dependentes antigos.

## Comandos guiados

```bash
UID_DEP=$(oc get deployment obs-web -n ac03-projetos -o jsonpath='{.metadata.uid}')
cat <<EOF | oc apply -n ac03-projetos -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: ac03-dependente
  labels:
    academy.openshift.dev/managed-by: academia
  ownerReferences:
    - apiVersion: apps/v1
      kind: Deployment
      name: obs-web
      uid: ${UID_DEP}
data:
  nota: "apagado junto com o Deployment obs-web"
EOF
oc get configmap ac03-dependente -n ac03-projetos -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'

oc delete deployment obs-web -n ac03-projetos --cascade=orphan   # RS e pods ficam
oc get rs,pods -n ac03-projetos -l app=obs-web                   # continuam lá
oc get configmap ac03-dependente -n ac03-projetos -o name 2>&1   # com orphan, o ConfigMap também fica (sem dono)
oc get rs -n ac03-projetos -l app=obs-web -o jsonpath='{.items[0].metadata.ownerReferences}{"\n"}'   # vazio

scripts/safe-cleanup.sh -n ac03-projetos --execute               # remove o que sobrou, por rótulo
oc apply -f manifests/apps-exemplo/observacao-httpd.yaml -n ac03-projetos   # recria o alvo
```

## Repetições

1. Repita, mas apague o Deployment **sem** `--cascade=orphan`: o `ac03-dependente` some sozinho?
2. Repita com `--cascade=foreground` e observe `oc get deployment obs-web -n ac03-projetos -o jsonpath='{.metadata.deletionTimestamp}'` durante a remoção.
3. Siga a cadeia completa Pod → ReplicaSet → Deployment com jsonpath.
4. Tente criar um ConfigMap dono de um objeto de **outro** namespace e leia o resultado (o coletor trata a referência como inválida).
5. Liste todos os objetos do projeto que têm algum dono: `oc get cm,rs,pods -n ac03-projetos -o json | jq -r '.items[] | select(.metadata.ownerReferences) | .kind + "/" + .metadata.name'`.

## Desafio sem pista

Faça um ConfigMap que seja apagado automaticamente quando **o Service** `obs-web` for apagado (e não quando o Deployment
for), prove o comportamento e restaure o alvo.

## Diagnóstico controlado

- **Sintoma:** depois de recriar `obs-web`, um ConfigMap que "pertencia" a ele não é mais apagado quando o Deployment é removido.
- **Hipóteses:** a referência aponta para o `uid` do Deployment antigo.
- **Investigação:** compare `oc get deploy obs-web -o jsonpath='{.metadata.uid}'` com `ownerReferences[0].uid` do ConfigMap.
- **Reversão:** apague o ConfigMap pelo rótulo ou refaça a referência com o `uid` atual.
