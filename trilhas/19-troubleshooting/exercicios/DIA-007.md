## Conceito

> **Diagnóstico cego.** Aplique o caso **sem ler o manifesto**: o arquivo diz só o sintoma. Cada caso tem
> **mais de um defeito**, em camadas diferentes. Siga o método do DIA-001 e anote cada hipótese antes de testá-la.
> Corrija no cluster (`oc patch`, `oc set ...`) ou em uma cópia em `/tmp/ac19`, nunca no repositório.

Sintoma relatado: o robô (SA `ac19-c5-robo`) recebe Forbidden ao escalar o `ac19-c5`. Teste como ele com `--as`.

## Comandos guiados

```bash
oc apply -f manifests/casos/caso-05.yaml -n ac19-casos
S=system:serviceaccount:ac19-casos:ac19-c5-robo
oc scale deployment/ac19-c5 --replicas=2 -n ac19-casos --as=$S 2>&1 | head -2
oc auth can-i update deployments/scale -n ac19-casos --as=$S
# leia a mensagem por partes (RBC-014) e depois os objetos de RBAC do caso
```

## Repetições

1. Que parte da mensagem Forbidden apontou o problema?
2. Depois de corrigir o primeiro defeito, a mensagem mudou?
3. Por que `oc create role --resource=deployments.apps` teria evitado um dos defeitos?
4. O binding referenciava um sujeito existente?
5. Refaça do zero sem notas.

## Desafio sem pista

Escreva a Role e o RoleBinding corretos do zero (em YAML), aplique-os por cima dos do caso e prove com `can-i` que o robô só pode escalar (não pode, por exemplo, apagar o Deployment).

## Diagnóstico controlado

- **Sintoma:** mesmo com a Role, `can-i update deployments/scale` responde `no`.
- **Hipóteses:** (a) binding para um sujeito com nome errado; (b) regra no grupo de API errado.
- **Investigação:** `subjects` do RoleBinding; `apiGroups` da Role; `oc get sa`.
- **Reversão:** corrija os dois (TS-048, RBC-014).

## Validação

```bash
oc auth can-i update deployments/scale -n ac19-casos --as=system:serviceaccount:ac19-casos:ac19-c5-robo    # yes
```
