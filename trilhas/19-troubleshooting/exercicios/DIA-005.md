## Objetivo e indicador de sucesso

Diagnosticar e corrigir o caso 03, em que a Route responde "Application is not available".

**Indicador de sucesso:** `curl` na Route da `ocp-admin` recebe resposta HTTP do httpd (403 da página padrão é sucesso de rede).

## Conceito

> **Diagnóstico cego.** Aplique o caso **sem ler o manifesto**: o arquivo diz só o sintoma. Cada caso tem
> **mais de um defeito**, em camadas diferentes. Siga o método do DIA-001 e anote cada hipótese antes de testá-la.
> Corrija no cluster (`oc patch`, `oc set ...`) ou em uma cópia em `/tmp/ac19`, nunca no repositório.

Sintoma relatado: a Route responde 503. Lembre do caminho da Trilha 07: cliente → DNS → router → Route → Service → endpoints → pod.

## Comandos guiados

```bash
oc apply -f manifests/casos/caso-03.yaml -n ac19-casos
sleep 30
H=$(oc get route ac19-c3 -n ac19-casos -o jsonpath='{.spec.host}'); curl -sS -m 5 -o /dev/null -w '%{http_code}\n' "http://$H/"
# andar por andar...
```

## Repetições

1. O 503 vinha de qual componente? (router, pela página padrão)
2. Que andar estava errado primeiro? Os pods estavam prontos?
3. Corrigido o primeiro, a Route passou a responder?
4. Por que uma probe HTTP em `/` falha na UBI? (RES-004)
5. Refaça do zero sem notas.

## Desafio sem pista

Corrija de forma que a readiness continue sendo HTTP (não TCP), mas em um caminho que de fato responde 200.

## Diagnóstico controlado

- **Sintoma:** pods `Running` mas `0/1`; Route 503.
- **Hipóteses:** readiness falhando (andar 6), deixando o Service sem endpoints prontos (andar 7).
- **Investigação:** `oc describe pod` (Readiness probe failed); EndpointSlices.
- **Reversão:** ajuste a probe; depois confira o `targetPort`.

## Validação

```bash
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' "http://$(oc get route ac19-c3 -n ac19-casos -o jsonpath='{.spec.host}')/"    # 200 ou 403, não 503
```
