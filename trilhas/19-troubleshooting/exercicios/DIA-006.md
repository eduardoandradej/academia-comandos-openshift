Diagnosticar e corrigir o caso 04 lendo **todos** os motivos da mensagem do agendador.

## Conceito

> **Diagnóstico cego.** Aplique o caso **sem ler o manifesto**: o arquivo diz só o sintoma. Cada caso tem
> **mais de um defeito**, em camadas diferentes. Siga o método do DIA-001 e anote cada hipótese antes de testá-la.
> Corrija no cluster (`oc patch`, `oc set ...`) ou em uma cópia em `/tmp/ac19`, nunca no repositório.

Sintoma relatado: "o relatório nunca sai do Pending". A mensagem do agendador lista **todos** os filtros que falharam.

## Comandos guiados

```bash
oc apply -f manifests/casos/caso-04.yaml -n ac19-casos
sleep 15; oc get pods -n ac19-casos -l app=ac19-c4
oc describe pod -n ac19-casos -l app=ac19-c4 | sed -n '/Events:/,$p'
```

## Repetições

1. Quantos motivos a mensagem `FailedScheduling` traz?
2. Corrija só um deles: a mensagem muda?
3. Quanto de CPU o nó tem alocável? (ADM-001, perfil admin)
4. Que valores de request fazem sentido para um httpd de treino?
5. Refaça do zero sem notas.

## Desafio sem pista

Resolva com **um** comando `oc patch` (JSON Patch) que corrige os dois motivos ao mesmo tempo.

## Diagnóstico controlado

- **Sintoma:** `0/1 nodes are available: 1 Insufficient cpu, 1 node(s) didn't match Pod's node affinity/selector`.
- **Hipóteses:** dois filtros do agendador falharam ao mesmo tempo.
- **Investigação:** `nodeSelector` e `resources.requests` do pod.
- **Reversão:** remova o seletor e ajuste o request.

## Validação

```bash
oc get pods -n ac19-casos -l app=ac19-c4 -o jsonpath='{.items[0].status.phase}{"\n"}'    # Running
```
