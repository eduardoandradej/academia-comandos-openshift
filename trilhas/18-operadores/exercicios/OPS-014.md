## Objetivo e indicador de sucesso

Aplicar, só com leitura, um roteiro fixo a um ClusterOperator fora do ideal: condições → relatedObjects → pods →
eventos → logs do operador → coleta planejada.

**Indicador de sucesso:** um "relatório de incidente" de 6 linhas para um operador (real ou o mais recente a ter mudado de estado).

## Conceito

> **Somente observação.** Nesta trilha nenhum comando altera operadores, `ClusterVersion`, `MachineConfig`, OLM ou
> o nó. Onde aparece uma mudança, ela vem com `--dry-run=server` (validada, não gravada) ou como plano escrito.
> No SNO, mexer nesses objetos pode reiniciar o único nó ou derrubar o cluster.

| # | Pergunta | Comando |
|---|---|---|
| 1 | Qual condição e mensagem? | `oc get co X -o json \| jq '.status.conditions'` |
| 2 | O que ele gerencia? | `relatedObjects` |
| 3 | Os pods do operand e do operador estão bem? | `oc get pods -n <ns>` |
| 4 | Que eventos de aviso? | `oc get events -n <ns> --field-selector type=Warning` |
| 5 | O que o operador registra? | `oc logs deploy/<operador> -n <ns-operator> --tail=50` |
| 6 | Coleta para suporte | `oc adm inspect co/X` (planejado, VERMELHO) |

Ler logs e eventos é seguro; reiniciar pods ou editar objetos do operador não é.

## Comandos guiados

```bash
CO=$(oc get co -o json | jq -r '[.items[] | {n: .metadata.name, t: ([.status.conditions[].lastTransitionTime] | max)}] | sort_by(.t) | last.n')
echo "operador analisado: $CO"
oc get co "$CO" -o json | jq -r '.status.conditions[] | "\(.type)=\(.status) \(.reason // "") \(.message // "" | .[0:120])"'
NSS=$(oc get co "$CO" -o json | jq -r '[.status.relatedObjects[] | select(.resource=="namespaces") | .name] | unique | join(" ")'); echo "namespaces: $NSS"
for n in $NSS; do echo "== $n"; oc get pods -n "$n" --no-headers 2>/dev/null | awk '{print $3}' | sort | uniq -c; done
for n in $NSS; do oc get events -n "$n" --field-selector type=Warning --no-headers 2>/dev/null | tail -3; done
OPNS=$(echo "$NSS" | tr ' ' '\n' | grep -m1 -- '-operator$'); [ -n "$OPNS" ] && oc logs -n "$OPNS" "$(oc get deploy -n "$OPNS" -o name | head -1)" --tail=20 2>/dev/null
```

## Repetições

1. Aplique o roteiro ao operador `ingress` e ao `monitoring`.
2. Que operador mudou de estado por último? Por quê?
3. Nos logs do operador, encontre a última reconciliação bem-sucedida.
4. Quanto ocuparia um `oc adm inspect co/<operador>`? (planeje; não execute)
5. Escreva o roteiro de memória.

## Desafio sem pista

Escreva `incidente_co <operador>` que imprime o relatório de 6 linhas: condição atual, namespaces, pods não Running,
último aviso, última linha de erro do log do operador e o comando de coleta sugerido.

## Diagnóstico controlado

- **Sintoma:** `authentication` em `Degraded=True` com `OAuthServerRouteEndpointAccessibleControllerDegraded`.
- **Hipóteses:** o OAuth não alcança a própria Route (DNS do `*.apps` ou router).
- **Investigação:** pods do router; `getent hosts oauth-openshift.apps.ocp.example.lab` (na `ocp-admin` e no cluster).
- **Reversão:** corrigir DNS/router é manutenção do HomeLab; nada a alterar em `openshift-*` pela Academia.
