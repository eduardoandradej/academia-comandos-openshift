# OPS-013 — Monitoramento: alertas ativos pela API (leitura)

## Identificação

- **ID:** OPS-013
- **Trilha:** [18 — Operadores e manutenção](../README.md)
- **Referência didática:** DO280 — monitoramento do cluster.
- **Fichas de comando:** [`oc-operadores-manutencao`](../../../catalogo/fichas/oc-operadores-manutencao.md)

## Objetivo e indicador de sucesso

Ler os alertas ativos e regras do monitoramento da plataforma pela API (Thanos Querier/Alertmanager), com o token do
admin em variável, sem entrar em pods do sistema.

**Indicador de sucesso:** a lista de alertas ativos com severidade — e a explicação do sempre presente `Watchdog`.

## Nível

**Nível:** Intermediário

## Duração e repetições

- **Duração sugerida:** 15 min
- **Repetições:** 3×

## Contexto

- **Terminal:** `student@ocp-admin`, na raiz do repositório clonado (`cd ~/academia-comandos-openshift`)
- **Perfil:** `admin` (somente leitura)
- **Projeto:** cluster (leitura)
- **Impacto:** LEITURA

## Pré-flight

```bash
source scripts/perfis.sh && ac-admin
oc whoami                            # admin — SOMENTE LEITURA nesta trilha
scripts/preflight.sh                 # sem FALHA
```

REQUER PREPARAÇÃO: curinga `*.apps` resolvendo na `ocp-admin` (Routes do monitoramento).

## Conceito

> **Somente observação.** Nesta trilha nenhum comando altera operadores, `ClusterVersion`, `MachineConfig`, OLM ou
> o nó. Onde aparece uma mudança, ela vem com `--dry-run=server` (validada, não gravada) ou como plano escrito.
> No SNO, mexer nesses objetos pode reiniciar o único nó ou derrubar o cluster.

| Componente | Route em `openshift-monitoring` | Uso |
|---|---|---|
| Thanos Querier | `thanos-querier` | consultas PromQL e `/api/v1/alerts` |
| Alertmanager | `alertmanager-main` | alertas agrupados e silêncios |
| regras | `PrometheusRule` (CRD) | o que gera cada alerta |

O alerta `Watchdog` está **sempre** disparando: prova que o pipeline de alertas funciona. No HomeLab, o Prometheus não
tem armazenamento persistente: histórico curto e perdido em reinícios.

## Comandos guiados

```bash
oc get pods -n openshift-monitoring --no-headers | awk '{print $3}' | sort | uniq -c
oc get route -n openshift-monitoring
TQ=$(oc get route thanos-querier -n openshift-monitoring -o jsonpath='{.spec.host}')
T=$(oc whoami -t)
curl -sSk -H "Authorization: Bearer $T" "https://$TQ/api/v1/alerts" | jq -r '.data.alerts[] | "\(.labels.severity)\t\(.labels.alertname)\t\(.labels.namespace // "-")"' | sort | uniq -c | sort -rn
curl -sSk -H "Authorization: Bearer $T" "https://$TQ/api/v1/query" --data-urlencode 'query=count(up == 0) by (job)' | jq -r '.data.result[] | "\(.metric.job) fora: \(.value[1])"'
unset T
oc get prometheusrule -A --no-headers | wc -l
```

## Repetições

1. Quais alertas `warning`/`critical` estão ativos? Algum ligado aos seus projetos `ac*`?
2. Consulte `node_memory_MemAvailable_bytes` e calcule a memória livre do nó em GiB.
3. Por que nunca imprimir `oc whoami -t`?
4. Encontre a PrometheusRule que define um dos alertas ativos.
5. O que se perde por o Prometheus não ter PVC no HomeLab?

## Desafio sem pista

Escreva `alertas` que imprima só os alertas não-`Watchdog`, com severidade, nome, namespace e há quanto tempo estão ativos (`activeAt`).

## Diagnóstico controlado

- **Sintoma:** `curl` responde `401 Unauthorized`.
- **Hipóteses:** token vazio (perfil sem sessão), ou usuário sem permissão de ler métricas.
- **Investigação:** `oc whoami`; `oc auth can-i get pods --subresource=metrics`... (o admin tem acesso).
- **Reversão:** `ac-admin` e repita; nunca use o token do instalador.

## Validação

```bash
oc get route thanos-querier -n openshift-monitoring -o name
```

