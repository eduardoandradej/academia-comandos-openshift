## Objetivo e indicador de sucesso

Descobrir quantas APIs personalizadas existem, de quem são e como ler o esquema de um recurso personalizado.

**Indicador de sucesso:** você aponta o grupo de API, o escopo e o dono de três CRDs, e explica um campo com `oc explain`.

## Conceito

> **Somente observação.** Nesta trilha nenhum comando altera operadores, `ClusterVersion`, `MachineConfig`, OLM ou
> o nó. Onde aparece uma mudança, ela vem com `--dry-run=server` (validada, não gravada) ou como plano escrito.
> No SNO, mexer nesses objetos pode reiniciar o único nó ou derrubar o cluster.

Um **CRD** acrescenta um tipo à API (`IngressController`, `MachineConfig`, `NetworkPolicy` não — esse é nativo).
Apagar um CRD apaga **todos** os objetos daquele tipo no cluster: por isso CRDs são VERMELHO absoluto.

## Comandos guiados

```bash
oc get crd --no-headers | wc -l
oc get crd -o json | jq -r '.items[] | .spec.group' | sort | uniq -c | sort -rn | head
oc get crd ingresscontrollers.operator.openshift.io -o jsonpath='{.spec.scope} {.spec.versions[*].name}{"\n"}'
oc api-resources --api-group=machineconfiguration.openshift.io
oc explain ingresscontroller.spec.replicas --api-version=operator.openshift.io/v1
```

## Repetições

1. Quantos CRDs são de escopo `Cluster` e quantos `Namespaced`?
2. Qual grupo tem mais CRDs? Por quê?
3. Que versões de API o CRD `machineconfigs` serve?
4. `oc get crd <x> -o jsonpath='{.metadata.annotations}'` — há anotação de dono/operador?
5. Explique por que apagar um CRD é irreversível na prática.

## Desafio sem pista

Para os CRDs dos grupos `*.openshift.io`, conte quantos objetos existem de cada tipo (só leitura) e mostre os 5 tipos mais usados.

- **Investigação:** `oc get crd | grep -i lvm`; OPS-006.
- **Reversão:** nada a fazer: o tipo só existe depois da instalação (TS-007).
