## Conceito

| Passo (cluster com vários nós) | Comando | No SNO |
|---|---|---|
| isolar | `oc adm cordon <nó>` | nada novo é agendado — **inclusive** pods do sistema que reiniciarem |
| drenar | `oc adm drain <nó>` | despeja tudo, inclusive API, router, DNS: o cluster para |
| reiniciar | reboot / MCO | indisponibilidade total até voltar |
| liberar | `oc adm uncordon <nó>` | só se o cluster voltou |

**Proibidos na Academia** (VERMELHO, nunca automatizar). A manutenção do SNO segue a apostila do HomeLab:
desligamento controlado da VM, com janela e acesso de recuperação testado.

## Comandos guiados

```bash
N=$(oc get nodes -o jsonpath='{.items[0].metadata.name}')
oc get node "$N" -o jsonpath='isolado={.spec.unschedulable}{"\n"}'                     # vazio/false
oc get node "$N" -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'
oc get pdb -A -o json | jq -r '.items[] | select(.status.disruptionsAllowed==0) | "\(.metadata.namespace)/\(.metadata.name)"'   # PDBs que travariam um drain
oc adm drain --help | sed -n '1,12p'                                                     # só a ajuda
```

## Diagnóstico controlado

- **Sintoma:** depois de um `cordon` acidental, pods do sistema que reiniciaram ficam `Pending`.
- **Hipóteses:** nó marcado `unschedulable`.
- **Investigação:** `oc get node -o jsonpath='{.spec.unschedulable}'`.
- **Reversão:** `oc adm uncordon <nó>` — ação de recuperação, feita por quem administra o HomeLab.

## Validação

```bash
[ "$(oc get nodes -o jsonpath='{.items[0].spec.unschedulable}')" != true ] && echo "nó agendável"
```
