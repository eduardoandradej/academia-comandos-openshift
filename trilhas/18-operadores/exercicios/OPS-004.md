## Objetivo e indicador de sucesso

Encontrar, só com leitura, os campos que mudam o comportamento dos operadores (`managementState`,
`unsupportedConfigOverrides`, `overrides` do CVO) e entender por que alterá-los compromete o suporte e o cluster.

**Indicador de sucesso:** você lista os operadores com `managementState` diferente de `Managed` e confirma que não há overrides não suportados.

## Conceito

> **Somente observação.** Nesta trilha nenhum comando altera operadores, `ClusterVersion`, `MachineConfig`, OLM ou
> o nó. Onde aparece uma mudança, ela vem com `--dry-run=server` (validada, não gravada) ou como plano escrito.
> No SNO, mexer nesses objetos pode reiniciar o único nó ou derrubar o cluster.

| Campo | Valores | Efeito |
|---|---|---|
| `managementState` (CR do operador) | `Managed`, `Unmanaged`, `Removed` | `Unmanaged`: o operador para de reconciliar; `Removed`: remove o operand |
| `unsupportedConfigOverrides` | qualquer | ajustes fora do suporte; podem quebrar atualizações |
| `clusterversion.spec.overrides` | lista | tira um componente do controle do CVO (`Upgradeable=False`) |

O registry interno `Removed` (IMG-010) é um exemplo **legítimo**; os demais devem estar `Managed`.

## Comandos guiados

```bash
oc get clusterversion version -o jsonpath='{.spec.overrides}{"\n"}'                     # vazio é o esperado
for r in kubeapiserver kubecontrollermanager kubescheduler etcd network console authentication; do
  printf '%s: %s\n' "$r" "$(oc get "$r.operator.openshift.io" cluster -o jsonpath='{.spec.managementState} overrides={.spec.unsupportedConfigOverrides}' 2>/dev/null)"
done
oc get configs.imageregistry.operator.openshift.io cluster -o jsonpath='image-registry: {.spec.managementState}{"\n"}'
oc get configs.samples.operator.openshift.io cluster -o jsonpath='samples: {.spec.managementState}{"\n"}' 2>/dev/null
```

## Repetições

1. Algum operador `Unmanaged`? O que deixaria de acontecer?
2. Por que o registry está `Removed` no HomeLab? (IMG-010)
3. Que condição do CVO fica `False` quando há `overrides`?
4. Leia `oc explain kubeapiserver.spec.unsupportedConfigOverrides --api-version=operator.openshift.io/v1`.
5. Explique em duas frases por que a Academia proíbe mexer nesses campos.

## Desafio sem pista

Escreva uma verificação que percorra **todos** os recursos do grupo `operator.openshift.io` com nome `cluster` e
liste os que têm `unsupportedConfigOverrides` não vazio ou `managementState` ≠ `Managed`.

## Diagnóstico controlado

- **Sintoma:** `Upgradeable=False` no CVO com mensagem sobre `overrides`.
- **Hipóteses:** alguém pôs componentes em `spec.overrides` do ClusterVersion.
- **Investigação:** `oc get clusterversion version -o jsonpath='{.spec.overrides}'`.
- **Reversão:** manutenção do cluster (fora da Academia): remover o override com o procedimento oficial.

## Validação

```bash
[ -z "$(oc get clusterversion version -o jsonpath='{.spec.overrides}')" ] && echo "sem overrides no CVO"
```
