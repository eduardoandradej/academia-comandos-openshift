## Objetivo e indicador de sucesso

Seguir, para um ClusterOperator, a cadeia operador → recurso de configuração → objetos gerados → pods, usando
`relatedObjects`, sem alterar nada.

**Indicador de sucesso:** para o operador `ingress`, você mostra o Deployment do operador, o `IngressController`, o Deployment do router e seus pods.

## Conceito

> **Somente observação.** Nesta trilha nenhum comando altera operadores, `ClusterVersion`, `MachineConfig`, OLM ou
> o nó. Onde aparece uma mudança, ela vem com `--dry-run=server` (validada, não gravada) ou como plano escrito.
> No SNO, mexer nesses objetos pode reiniciar o único nó ou derrubar o cluster.

Padrão de operador: um **controlador** observa um **recurso de configuração** (CR) e cria/ajusta objetos para que o
estado real siga o desejado (**reconciliação**). O ClusterOperator lista em `status.relatedObjects` o que ele gerencia.

| Operador | CR de configuração | Operand |
|---|---|---|
| `ingress` | `ingresscontroller/default` | router em `openshift-ingress` |
| `dns` | `dns.operator/default` | CoreDNS em `openshift-dns` |
| `image-registry` | `configs.imageregistry/cluster` | registry interno |

## Comandos guiados

```bash
oc get co ingress -o json | jq -r '.status.relatedObjects[] | "\(.resource)\t\(.namespace // "-")\t\(.name)"'
oc get deployment -n openshift-ingress-operator
oc get ingresscontroller default -n openshift-ingress-operator -o jsonpath='{.spec}{"\n"}{.status.availableReplicas}{"\n"}'
oc get deployment -n openshift-ingress -o wide
oc get pods -n openshift-ingress -o wide
oc get deployment router-default -n openshift-ingress -o jsonpath='{.metadata.ownerReferences}{"\n"}'
```

## Repetições

1. Faça a mesma cadeia para o operador `dns`.
2. Quem é o dono (`ownerReferences`) do Deployment `router-default`?
3. Que namespaces o operador `monitoring` lista?
4. Por que existem dois namespaces (`-operator` e o do operand)?
5. Desenhe a cadeia do `ingress` de memória.

## Desafio sem pista

Escreva `cadeia <clusteroperator>` que lista os relatedObjects e, para cada namespace citado, os Deployments e o número de pods prontos.

## Diagnóstico controlado

- **Sintoma:** alguém editou o Deployment `router-default` e a mudança "sumiu" em segundos.
- **Hipóteses:** reconciliação: o operador restaura o objeto que ele gera a partir do CR.
- **Investigação:** `ownerReferences`; eventos do Deployment; quem é o gerenciador (`managedFields`).
- **Reversão:** mudanças suportadas vão no CR (`ingresscontroller`), e só com janela de manutenção — não na Academia.
