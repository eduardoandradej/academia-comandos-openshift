## Objetivo e indicador de sucesso

Conceder `view`, depois `edit`, depois `admin` à SA `ac15-leitor` e medir com `can-i` o que cada papel acrescenta.

**Indicador de sucesso:** uma tabela papel × ação mostrando, por exemplo, que só `admin` gerencia RoleBindings e que `view` não lê Secrets.

## Conceito

> **Como testamos permissões sem criar usuários.** Uma *service account* (SA) do projeto faz o papel de "colega":
> `--as=system:serviceaccount:ac15-rbac:ac15-leitor` pergunta à API "e se fosse ela?". Quem é admin do projeto pode
> se passar por SAs do próprio projeto. Usuários do HTPasswd não são criados nesta trilha (RBC-013).

| Papel | Pode | Não pode |
|---|---|---|
| `view` | ler quase tudo | ler Secrets; alterar qualquer coisa |
| `edit` | criar/alterar workloads, Secrets, Services, Routes | gerenciar RBAC, quotas |
| `admin` | tudo no projeto, inclusive RoleBindings | quotas/LimitRanges (são do admin do cluster) |

`oc policy add-role-to-user PAPEL USUÁRIO` ou `-z SA` cria (ou estende) um RoleBinding no projeto.

## Comandos guiados

```bash
acoes=("list pods" "list secrets" "create deployments" "create rolebindings" "delete resourcequotas")
tabela() { for a in "${acoes[@]}"; do printf '%-26s %s\n' "$a" "$(oc auth can-i $a -n ac15-rbac --as=system:serviceaccount:ac15-rbac:ac15-leitor)"; done; }
echo "== sem papel"; tabela
oc policy add-role-to-user view -z ac15-leitor -n ac15-rbac;  echo "== view";  tabela
oc policy add-role-to-user edit -z ac15-leitor -n ac15-rbac;  echo "== +edit"; tabela
oc policy add-role-to-user admin -z ac15-leitor -n ac15-rbac; echo "== +admin"; tabela
oc get rolebindings -n ac15-rbac -o wide
```

## Repetições

1. Remova `admin` e `edit` (`oc policy remove-role-from-user ... -z ac15-leitor`) e confira que sobra `view`.
2. Quantas regras tem cada papel? `oc get clusterrole view -o json | jq '.rules | length'`.
3. `oc describe clusterrole edit | grep -i secrets`.
4. Quem é admin do projeto por padrão? (`oc get rolebinding admin -n ac15-rbac -o yaml`)
5. Repita a tabela para `ac15-robo` sem papéis.

## Desafio sem pista

Prove que `view` não lê Secrets mas consegue ler **ConfigMaps** e **pods/log**, e que `edit` consegue `pods/exec` — tudo por `can-i`.

## Diagnóstico controlado

- **Sintoma:** depois de `add-role-to-user edit`, a SA ainda recebe Forbidden ao criar RoleBindings.
- **Hipóteses:** comportamento correto: `edit` não gerencia RBAC.
- **Investigação:** `oc describe clusterrole edit | grep -i rolebinding`.
- **Reversão:** se ela realmente precisar, `admin` (com critério) ou um papel próprio (RBC-005).

## Validação

```bash
oc auth can-i list pods -n ac15-rbac --as=system:serviceaccount:ac15-rbac:ac15-leitor     # yes
```

## Limpeza segura

```bash
oc policy remove-role-from-user admin -z ac15-leitor -n ac15-rbac
oc policy remove-role-from-user edit -z ac15-leitor -n ac15-rbac
```

Fica só o `view` para os próximos exercícios.
