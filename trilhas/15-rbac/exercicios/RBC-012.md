## Objetivo e indicador de sucesso

Descobrir qual SCC admitiu um pod, quem pode usar cada SCC e por que um pod que pede `runAsUser: 0` é recusado — sem conceder SCCs.

**Indicador de sucesso:** você mostra a anotação `openshift.io/scc` de um pod, a recusa de um pod root e o YAML do binding que liberaria `anyuid` (só dry-run).

## Conceito

SCCs decidem **como** um pod pode rodar (UID, capabilities, volumes, host). O acesso a uma SCC é RBAC: o verbo `use`
no recurso `securitycontextconstraints/<nome>`. A admissão escolhe a SCC mais restritiva que o pod satisfaz entre as
que o usuário **ou a SA do pod** podem usar.

| SCC | Permite |
|---|---|
| `restricted-v2` (padrão) | UID arbitrário do intervalo do projeto, sem capabilities extras |
| `nonroot-v2` | qualquer UID ≠ 0 |
| `anyuid` | qualquer UID, inclusive 0 |
| `privileged` | tudo — **proibida** na Academia |

## Comandos guiados

```bash
oc run ac15-normal --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac15-rbac --labels=academy.openshift.dev/managed-by=academia
oc get pod ac15-normal -n ac15-rbac -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'
oc get pod ac15-normal -n ac15-rbac -o jsonpath='{.spec.containers[0].securityContext.runAsUser}{"\n"}'
oc run ac15-root --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac15-rbac --labels=academy.openshift.dev/managed-by=academia \
  --overrides='{"spec":{"securityContext":{"runAsUser":0}}}' 2>&1 | head -3
oc auth can-i use scc/anyuid -n ac15-rbac --as=system:serviceaccount:ac15-rbac:default
oc adm policy add-scc-to-user anyuid -z ac15-robo -n ac15-rbac --dry-run=client -o yaml
oc get namespace ac15-rbac -o jsonpath='{.metadata.annotations.openshift\.io/sa\.scc\.uid-range}{"\n"}'
```

## Repetições

1. Que UID o `ac15-normal` recebeu? Está no intervalo da anotação do namespace?
2. (admin, leitura) `oc get scc` e `oc describe scc restricted-v2 | head -30`.
3. (admin, leitura) `oc adm policy who-can use scc/privileged` — quem são?
4. O `ac15-root` foi criado? Leia a mensagem de recusa (`unable to validate against any security context constraint`).
5. Por que a correção certa quase sempre é **a imagem**, não a SCC? (IMG-003)

## Desafio sem pista

Use `oc adm policy scc-subject-review` (ou `scc-review`) para perguntar, sem criar o pod, quais SCCs admitiriam o pod
root com a SA `default` e com a SA `ac15-robo`.

## Diagnóstico controlado

- **Sintoma:** `pods "ac15-root" is forbidden: unable to validate against any security context constraint: [... runAsUser: Invalid value: 0: must be in the ranges ...]`.
- **Hipóteses:** nenhuma SCC permitida ao usuário/SA aceita UID 0.
- **Investigação:** `oc auth can-i use scc/anyuid --as=...`; a mensagem lista as SCCs avaliadas.
- **Reversão:** use uma imagem que aceite UID arbitrário. Conceder `anyuid`/`privileged` não é uma correção na Academia.

## Validação

```bash
oc get pod ac15-normal -n ac15-rbac -o jsonpath='{.metadata.annotations.openshift\.io/scc}{"\n"}'    # restricted-v2
```
