## Objetivo e indicador de sucesso

Criar uma Role que só lê pods e logs — e outra que só lê **um** ConfigMap pelo nome — e provar o menor privilégio.

**Indicador de sucesso:** a SA `ac15-robo` lê pods e logs, lê o ConfigMap `ac15-publico`, e recebe Forbidden em todo o resto.

## Conceito

> **Como testamos permissões sem criar usuários.** Uma *service account* (SA) do projeto faz o papel de "colega":
> `--as=system:serviceaccount:ac15-rbac:ac15-leitor` pergunta à API "e se fosse ela?". Quem é admin do projeto pode
> se passar por SAs do próprio projeto. Usuários do HTPasswd não são criados nesta trilha (RBC-013).

`oc create role NOME --verb=get,list,watch --resource=pods,pods/log [--resource-name=x]` cria uma Role no projeto.
Regras de bolso:

- liste **verbos** explícitos (nada de `*`);
- subrecursos são recursos à parte (`pods/log`, `pods/exec`);
- `resourceNames` restringe a objetos específicos — mas não funciona com `list`/`watch` (que não têm nome).

## Comandos guiados

```bash
oc create role ac15-leitor-pods --verb=get,list,watch --resource=pods,pods/log -n ac15-rbac
oc create configmap ac15-publico --from-literal=aviso=ola -n ac15-rbac
oc create configmap ac15-privado --from-literal=x=y -n ac15-rbac
oc create role ac15-so-publico --verb=get --resource=configmaps --resource-name=ac15-publico -n ac15-rbac
oc label role ac15-leitor-pods ac15-so-publico academy.openshift.dev/managed-by=academia -n ac15-rbac
oc create rolebinding ac15-robo-pods --role=ac15-leitor-pods --serviceaccount=ac15-rbac:ac15-robo -n ac15-rbac
oc create rolebinding ac15-robo-publico --role=ac15-so-publico --serviceaccount=ac15-rbac:ac15-robo -n ac15-rbac
S=system:serviceaccount:ac15-rbac:ac15-robo
for a in "list pods" "get pods/log" "get configmap/ac15-publico" "get configmap/ac15-privado" "list configmaps" "delete pods"; do
  printf '%-30s %s\n' "$a" "$(oc auth can-i $a -n ac15-rbac --as=$S)"; done
oc get configmap ac15-publico -n ac15-rbac --as=$S -o jsonpath='{.data.aviso}{"\n"}'
oc get configmaps -n ac15-rbac --as=$S 2>&1 | head -1          # Forbidden: list não respeita resourceNames
```

## Repetições

1. `oc describe role ac15-leitor-pods -n ac15-rbac`.
2. Acrescente `watch` em ConfigMaps com `resourceNames` e teste `oc get cm ac15-publico -w --as=...`.
3. Gere a Role em YAML (`--dry-run=client -o yaml`) e leia `rules`.
4. Use `oc auth reconcile -f role.yaml` (aplica Roles mesclando regras).
5. Crie uma Role para `deployments/scale` apenas (escalar sem editar).

## Desafio sem pista

Crie a Role `ac15-escalador` que permite **somente** escalar Deployments (ler e alterar `deployments/scale`) e ler
Deployments, e prove que a SA consegue `oc scale` mas não `oc set image`.

## Diagnóstico controlado

- **Sintoma:** com `resourceNames`, `oc get configmaps` (listar) dá Forbidden, mas `oc get configmap ac15-publico` funciona.
- **Hipóteses:** `list` não tem nome de objeto; `resourceNames` só vale para verbos sobre um objeto (`get`, `update`, `delete`, `patch`).
- **Investigação:** `oc auth can-i list configmaps --as=...` × `get configmap/ac15-publico`.
- **Reversão:** é o comportamento esperado; peça pelo nome.

## Validação

```bash
oc auth can-i get configmap/ac15-privado -n ac15-rbac --as=system:serviceaccount:ac15-rbac:ac15-robo; echo "(esperado: no)"
```
