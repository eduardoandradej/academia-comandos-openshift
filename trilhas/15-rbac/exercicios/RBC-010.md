## Objetivo e indicador de sucesso

Responder, para um projeto, "quem pode fazer o quê" de três formas: bindings, `who-can` e matriz `can-i` por sujeito.

**Indicador de sucesso:** um relatório de acesso do `ac15-rbac` que um auditor entenderia, incluindo herança por grupos.

## Conceito

| Pergunta | Ferramenta |
|---|---|
| que bindings existem? | `oc get rolebindings -n NS -o json \| jq` |
| quem pode X? | `oc adm policy who-can VERBO RECURSO -n NS` |
| o que Y pode? | `oc auth can-i --list -n NS --as=Y` |

`who-can` inclui quem tem acesso por papéis de cluster (admins) e por grupos virtuais.

## Comandos guiados

```bash
oc get rolebindings -n ac15-rbac -o json | jq -r '.items[] | .roleRef.name as $r | .subjects[]? | "\(.kind)\t\(.name)\t\($r)"' | sort
for v in "get secrets" "create pods/exec" "delete deployments" "create rolebindings"; do
  echo "== quem pode: $v"; oc adm policy who-can $v -n ac15-rbac 2>/dev/null | sed -n '/Users:/,/Groups:/p' | grep -v -E '^(Users|Groups):' | head -5
done
oc auth can-i --list -n ac15-rbac --as=system:serviceaccount:ac15-rbac:ac15-leitor | awk 'NR==1 || /pods|configmaps|secrets/'
```

## Repetições

1. Por que aparecem usuários que você não adicionou no `who-can`? (papéis de cluster)
2. Inclua os grupos (`Groups:`) no relatório.
3. Gere o relatório em CSV.
4. Compare o relatório de hoje com o de um projeto de trilha anterior.
5. Faça o relatório para `ac15-alheio` como admin.

## Desafio sem pista

Produza a matriz sujeito × ação (sujeitos: `developer`, `ac15-leitor`, `ac15-robo`; ações: ler pods, ler Secrets,
exec, criar Deployments, gerenciar RBAC), com ✔/✘ — usando impersonação de SA e, para `developer`, a própria sessão.

## Diagnóstico controlado

- **Sintoma:** `who-can` responde `Forbidden` para o developer.
- **Hipóteses:** `who-can` exige permissão de criar `localresourceaccessreviews` no projeto (admin do projeto tem).
- **Investigação:** `oc auth can-i create localresourceaccessreviews -n ac15-rbac`.
- **Reversão:** rode em um projeto seu ou como admin.
