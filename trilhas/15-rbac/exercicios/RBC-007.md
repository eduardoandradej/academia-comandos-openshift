# RBC-007 — Grupos: conceder a uma equipe, não a pessoas

## Identificação

- **ID:** RBC-007
- **Trilha:** [15 — Usuários, identidade e RBAC](../README.md)
- **Referência didática:** DO280 — grupos e RBAC.
- **Fichas de comando:** [`oc-policy-rbac`](../../../catalogo/fichas/oc-policy-rbac.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Criar (admin) um grupo de treino, colocar `developer` nele e dar ao grupo `edit` em um projeto que o developer não
possui, provando que a permissão vem do grupo.

**Indicador de sucesso:** `developer` passa de Forbidden para permitido em `ac15-alheio` só por entrar no grupo, e volta a Forbidden ao sair.

## Nível

**Nível:** Intermediário

## Duração e repetições

- **Duração sugerida:** 20 min
- **Repetições:** 3×

## Contexto

- **Terminal:** `student@ocp-admin`, na raiz do repositório clonado (`cd ~/academia-comandos-openshift`)
- **Perfil:** `admin` e `developer`
- **Projeto:** `ac15-alheio` (criado pelo admin)
- **Impacto:** MUTAÇÃO DE CLUSTER (1 grupo rotulado) · MUTAÇÃO LOCAL

## Pré-flight

```bash
source scripts/perfis.sh && ac-admin
oc whoami                            # admin
```

## Conceito

| Comando (admin) | Efeito |
|---|---|
| `oc adm groups new GRUPO [usuários]` | cria o grupo (objeto de cluster) |
| `oc adm groups add-users GRUPO u1 u2` / `remove-users` | membros |
| `oc policy add-role-to-group PAPEL GRUPO -n NS` | binding para o grupo |

No OpenShift, a pertença a grupos é avaliada **a cada requisição**: entrar ou sair do grupo vale na hora, sem novo login.
Os nomes dos grupos do DO280 (`dev-group`, `qa-group`) ficam reservados ao exercício do curso; aqui usamos `ac15-equipe`.

## Comandos guiados

```bash
oc new-project ac15-alheio --skip-config-write
oc label namespace ac15-alheio academy.openshift.dev/managed-by=academia
oc adm groups new ac15-equipe
oc label group ac15-equipe academy.openshift.dev/managed-by=academia academy.openshift.dev/trilha=15
oc policy add-role-to-group edit ac15-equipe -n ac15-alheio
oc auth can-i create deployments -n ac15-alheio --as=developer                     # no
oc adm groups add-users ac15-equipe developer
oc get group ac15-equipe -o jsonpath='{.users}{"\n"}'
oc auth can-i create deployments -n ac15-alheio --as=developer                     # yes
ac-dev; oc get pods -n ac15-alheio && echo "developer entrou via grupo"; ac-admin
oc adm groups remove-users ac15-equipe developer
oc auth can-i create deployments -n ac15-alheio --as=developer                     # no
ac-dev
```

## Repetições

1. `oc auth can-i ... --as=developer --as-group=ac15-equipe` (simula a pertença sem alterar o grupo).
2. Liste os grupos do cluster e os membros de cada um (admin).
3. Por que dar papéis a grupos é melhor que a pessoas? (rotatividade, auditoria)
4. O que acontece com o binding se o grupo for apagado? (fica apontando para um nome inexistente)
5. `oc describe rolebinding -n ac15-alheio`.

## Desafio sem pista

Monte, como admin, o arranjo "equipe de leitura": grupo `ac15-auditores` com `view` em `ac15-rbac` **e** em `ac15-alheio`,
e prove com `--as-group` que um membro lê pods nos dois mas não cria nada.

## Diagnóstico controlado

- **Sintoma:** o binding para o grupo existe, mas o usuário continua com Forbidden.
- **Hipóteses:** (a) usuário fora do grupo; (b) nome do grupo diferente no binding (`ac15-equipes`); (c) projeto errado.
- **Investigação:** `oc get group ac15-equipe -o yaml`; `subjects` do binding.
- **Reversão:** corrija o nome ou a pertença. Veja TS-048.

## Validação

```bash
KUBECONFIG="$HOME/.kube/ac-admin.kubeconfig" oc get group ac15-equipe -o name
```

## Limpeza segura

```bash
KUBECONFIG="$HOME/.kube/ac-admin.kubeconfig" oc delete group ac15-auditores --ignore-not-found
```

O grupo `ac15-equipe` e o projeto `ac15-alheio` são removidos no RBC-015.
