## Conceito

O `oc` lê credenciais de um **kubeconfig**: um arquivo com três listas — `clusters` (endereço e CA), `users`
(credenciais) e `contexts` (par cluster + usuário + namespace padrão). O arquivo usado é:

1. o(s) caminho(s) da variável `KUBECONFIG`, se definida (vários separados por `:`);
2. senão, `~/.kube/config`.

Na instalação do HomeLab, o `~/.bashrc` da `ocp-admin` passou a exportar
`KUBECONFIG=$HOME/openshift-lab/ocp422-sno/install/auth/kubeconfig`. Esse arquivo autentica com **certificado de
cliente** como `system:admin`: poder total, sem passar pelo OAuth. Ele é a chave de **recuperação** do cluster — não é
o perfil de estudo. Por isso, cada exercício começa conferindo a identidade.

Curiosidade que confunde: no kubeconfig do instalador, a entrada de usuário costuma se chamar `admin`, mas a
identidade real é `system:admin`. O nome dentro do arquivo é só um rótulo local; quem decide a identidade é a API.

## Comandos guiados

```bash
printenv KUBECONFIG                          # caminho(s) em uso; vazio = ~/.kube/config
grep -n 'KUBECONFIG' ~/.bashrc ~/.bash_profile 2>/dev/null   # de onde vem o valor
ls -l "${KUBECONFIG:-$HOME/.kube/config}"    # existe? permissões 600? (NÃO use cat)
oc whoami                                    # identidade segundo a API
oc whoami --show-server                      # endpoint da API
oc whoami --show-context                     # nome do contexto atual
oc config current-context                    # mesmo dado, lido só do arquivo local
oc config get-contexts                       # o asterisco (*) marca o contexto atual
oc auth can-i '*' '*' --all-namespaces       # "yes" = poderes de cluster-admin
```

Se a resposta de `oc whoami` for `system:admin` e o último comando responder `yes`, você está com a chave de
recuperação. Para os exercícios comuns, use os perfis dedicados (ORI-004).

## Repetições

1. `env | grep -i kube` — outras variáveis relacionadas.
2. `oc config view --minify -o jsonpath='{.contexts[0].context.user}{"\n"}'` — nome **local** da entrada de usuário.
3. Compare o resultado anterior com `oc whoami`. Por que diferem?
4. `oc auth can-i get nodes` e `oc auth can-i create projectrequests` — o que cada resposta diz sobre o perfil?
5. Abra um terminal novo e repita tudo: o resultado muda? Por quê?

## Desafio sem pista

Sem abrir nenhum arquivo de kubeconfig, prove com **três comandos diferentes** qual identidade, qual servidor e qual
contexto estão em uso. Em seguida, responda: essa identidade é adequada para um exercício comum? Justifique com a saída de um comando.

## Diagnóstico controlado

- **Sintoma:** em um terminal novo, `oc whoami` responde `system:admin`, embora você tenha feito login como `developer` em outro terminal.
- **Hipóteses:** (a) o `~/.bashrc` exporta o kubeconfig do instalador em todo shell novo; (b) o login gravou credenciais em outro arquivo; (c) cada terminal tem seu próprio ambiente.
- **Investigação:** `printenv KUBECONFIG` nos dois terminais; `grep -n KUBECONFIG ~/.bashrc`; `oc config get-contexts` em cada um.
- **Reversão:** nada foi alterado. A correção estrutural (um kubeconfig por perfil) é o ORI-004.

## Validação

```bash
oc whoami && oc whoami --show-server && oc whoami --show-context
```

Você deve conseguir dizer, para cada linha, se o valor é o esperado para o exercício que vai fazer.
