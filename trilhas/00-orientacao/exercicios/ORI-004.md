# ORI-004 — Um kubeconfig dedicado para cada perfil

## Identificação

- **ID:** ORI-004
- **Trilha:** [00 — Orientação e segurança](../README.md)
- **Referência didática:** DO180 — autenticação com `oc login`. DO280 — contas de administração e desenvolvimento.
- **Fichas de comando:** [`oc-login-logout`](../../../catalogo/fichas/oc-login-logout.md), [`oc-config`](../../../catalogo/fichas/oc-config.md), [`oc-whoami`](../../../catalogo/fichas/oc-whoami.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Criar `~/.kube/ac-developer.kubeconfig` e `~/.kube/ac-admin.kubeconfig` com `oc login`, sem tocar no kubeconfig do instalador.

**Indicador de sucesso:** `KUBECONFIG=~/.kube/ac-developer.kubeconfig oc whoami` responde `developer`, o equivalente
para `admin` responde `admin`, e a data/tamanho do kubeconfig do instalador não mudaram.

## Nível

**Nível:** Iniciante

## Duração e repetições

- **Duração sugerida:** 20 min
- **Repetições:** 5× (ciclos de logout/login)

## Contexto

- **Terminal:** `student@ocp-admin`, na raiz do repositório clonado (`cd ~/academia-comandos-openshift`)
- **Perfil:** `developer` e `admin` (login interativo; senhas de treino digitadas no prompt)
- **Projeto:** nenhum
- **Impacto:** MUTAÇÃO LOCAL REVERSÍVEL — cria arquivos em `~/.kube` (fora do repositório) e tokens OAuth de sessão

## Pré-flight

```bash
oc get --raw /readyz; echo                  # API pronta?
getent ahostsv4 api.ocp.example.lab         # o nome resolve na ocp-admin?
```

Pré-requisito: o ORI-003 confirmou o provedor `homelab-users`. Sem ele, este exercício **REQUER PREPARAÇÃO**.

## Conceito

`oc login` grava o token obtido **no kubeconfig em uso**. Se o `KUBECONFIG` do instalador estiver ativo, o token de
`developer` vai parar dentro do arquivo sigiloso de recuperação — misturando perfis. A solução é apontar `KUBECONFIG`
para um arquivo novo **antes** do login.

Sobre TLS: a API usa um certificado assinado por uma CA interna do cluster. Sem informar essa CA, o `oc login` pergunta
`Use insecure connections? (y/n)`. Em um HomeLab isolado, aceitar é tolerável; o caminho melhor é passar a CA com
`--certificate-authority`. O ConfigMap `kube-root-ca.crt` (presente em todo namespace) contém o pacote de CAs da API;
usá-lo aqui é uma proposta **a validar**: se o login reclamar de `x509`, volte ao modo interativo.

Senhas de treino (`developer`/`developer`, `admin`/`redhatocp`) valem **só neste HomeLab** e são digitadas no prompt
— nunca na linha de comando, para não irem ao histórico.

## Comandos guiados

```bash
mkdir -p ~/.kube && chmod 700 ~/.kube
INSTALL_KC="$HOME/openshift-lab/ocp422-sno/install/auth/kubeconfig"
stat -c '%y %s bytes' "$INSTALL_KC"           # "impressão" ANTES: data de modificação e tamanho

# CA da API em arquivo próprio (leitura com a sessão atual; conteúdo público, não é segredo)
oc get configmap kube-root-ca.crt -n default -o jsonpath='{.data.ca\.crt}' > ~/.kube/ocp-sno-ca.crt
grep -c 'BEGIN CERTIFICATE' ~/.kube/ocp-sno-ca.crt   # quantos certificados há no pacote

# Perfil developer
export KUBECONFIG="$HOME/.kube/ac-developer.kubeconfig"
oc login https://api.ocp.example.lab:6443 -u developer \
  --certificate-authority="$HOME/.kube/ocp-sno-ca.crt"   # a senha é pedida no prompt
chmod 600 "$KUBECONFIG"
oc whoami; oc whoami --show-context

# Perfil admin
export KUBECONFIG="$HOME/.kube/ac-admin.kubeconfig"
oc login https://api.ocp.example.lab:6443 -u admin \
  --certificate-authority="$HOME/.kube/ocp-sno-ca.crt"
chmod 600 "$KUBECONFIG"
oc whoami

stat -c '%y %s bytes' "$INSTALL_KC"           # DEPOIS: deve ser idêntico ao ANTES
```

Para alternar rapidamente, carregue as funções de perfil do repositório (não alteram nada além da variável):

```bash
source scripts/perfis.sh
ac-dev        # KUBECONFIG -> ~/.kube/ac-developer.kubeconfig
ac-admin      # KUBECONFIG -> ~/.kube/ac-admin.kubeconfig
ac-perfil     # mostra o perfil atual
```

## Repetições

1. `ac-dev; oc logout; oc whoami` (erro esperado) e `oc login -u developer` (reaproveita servidor e CA do contexto).
2. Repita o ciclo 1 cinco vezes, sem consultar. Cronometre a última.
3. `oc whoami -t | wc -c` — confirma que há token **sem exibi-lo** (nunca rode `oc whoami -t` sozinho em tela compartilhada).
4. `ls -l ~/.kube/` — todos os arquivos com `-rw-------`?
5. Em um terminal novo, rode `ac-perfil` antes e depois de `source scripts/perfis.sh; ac-admin`.

## Desafio sem pista

Deixe três terminais abertos, um por perfil (`developer`, `admin`, recuperação), e prove — sem abrir arquivos — qual é
qual. Depois encerre a sessão OAuth de `developer`, confirme que ela não vale mais e restabeleça-a.

## Diagnóstico controlado

- **Sintoma:** `error: x509: certificate signed by unknown authority` (ou a pergunta sobre conexão insegura).
- **Hipóteses:** (a) o arquivo de CA está vazio ou foi gerado com a sessão errada; (b) a CA certa não está no pacote; (c) o nome do servidor está diferente do certificado.
- **Investigação:** `test -s ~/.kube/ocp-sno-ca.crt && echo tem-conteudo`;
  `openssl s_client -connect api.ocp.example.lab:6443 -servername api.ocp.example.lab </dev/null 2>/dev/null | openssl x509 -noout -issuer -subject`
  e compare o emissor com `openssl crl2pkcs7 -nocrl -certfile ~/.kube/ocp-sno-ca.crt | openssl pkcs7 -print_certs -noout | grep subject`.
- **Reversão:** `rm -f ~/.kube/ocp-sno-ca.crt` e refaça o login sem `--certificate-authority`, aceitando o modo inseguro **apenas no HomeLab**.

## Validação

```bash
KUBECONFIG="$HOME/.kube/ac-developer.kubeconfig" oc whoami    # developer
KUBECONFIG="$HOME/.kube/ac-admin.kubeconfig" oc whoami        # admin
stat -c '%a' ~/.kube/ac-developer.kubeconfig ~/.kube/ac-admin.kubeconfig   # 600 e 600
```

## Limpeza segura

Os arquivos ficam em `~/.kube` (fora do repositório) e serão usados nas próximas trilhas. Ao fim do dia, encerre as
sessões: `ac-dev; oc logout` e `ac-admin; oc logout`. Para desfazer tudo:
`rm -f ~/.kube/ac-developer.kubeconfig ~/.kube/ac-admin.kubeconfig ~/.kube/ocp-sno-ca.crt`.
