## Conceito

A API do Kubernetes publica endpoints de saúde acessíveis a qualquer usuário autenticado (e, por padrão, também sem
autenticação):

| Endpoint | Pergunta que responde |
|---|---|
| `/livez` | o processo do kube-apiserver está vivo? |
| `/readyz` | ele está pronto para atender tráfego (inclui etcd e inicializações)? |
| `/readyz?verbose` | quais checagens internas passaram (`[+]`) ou falharam (`[-]`)? |
| `/version` | qual versão do Kubernetes o servidor executa? |

`oc get --raw` faz um GET direto em um caminho da API usando as credenciais do kubeconfig. `curl -k` faz o mesmo sem
credenciais e sem validar a CA — aceitável aqui porque só lemos saúde. Uma API "viva" pode não estar "pronta".

## Comandos guiados

```bash
oc get --raw /readyz; echo                         # 'ok' = pronta; o echo só quebra a linha
oc get --raw /livez; echo                          # 'ok' = viva
oc get --raw '/readyz?verbose'                     # aspas: o ? seria interpretado pelo shell
oc get --raw '/readyz?verbose' | grep -v '^\[+\]'  # mostra só o que NÃO passou (+ a linha final)
oc get --raw /version | jq .                       # versão do Kubernetes do servidor
curl -ksS https://api.ocp.example.lab:6443/readyz; echo   # -k sem CA, -s silencioso, -S mostra erros
curl -sS --cacert ~/.kube/ocp-sno-ca.crt https://api.ocp.example.lab:6443/livez; echo   # com CA (ORI-004)
time oc get --raw /readyz                          # latência aproximada da ida e volta
```

## Repetições

1. `oc get --raw '/livez?verbose'` — compare a lista com a do `/readyz`.
2. `oc get --raw /readyz/etcd; echo` — uma checagem individual pelo nome.
3. `curl -ksS -o /dev/null -w '%{http_code}\n' https://api.ocp.example.lab:6443/readyz` — só o código HTTP.
4. `oc get --raw /version | jq -r .gitVersion` — só a versão.
5. Repita o item 3 dez vezes em um laço curto: `for i in $(seq 10); do ...; done`. Os códigos variam?

## Desafio sem pista

Mostre, com dois clientes diferentes, que a API está pronta e qual versão do Kubernetes ela executa; meça quanto tempo
a verificação leva e diga qual checagem do `/readyz` envolve o banco de dados do cluster.

## Diagnóstico controlado

- **Sintoma:** `curl: (6) Could not resolve host`.
- **Como reproduzir sem risco:** `curl -ksS https://api.ocp.example.lab.invalid:6443/readyz` (domínio `.invalid` nunca resolve).
- **Hipóteses:** (a) erro de digitação; (b) a `ocp-admin` não usa o DNS `192.168.10.25`; (c) `dnsmasq-ocp` parado no host.
- **Investigação:** `getent ahostsv4 api.ocp.example.lab`; `grep nameserver /etc/resolv.conf`;
  `dig @192.168.10.25 api.ocp.example.lab +short` (se `bind-utils` estiver instalado).
- **Reversão:** nada a reverter. Alterar DNS do host é tarefa de manutenção fora desta trilha.

[ "$(curl -ksS https://api.ocp.example.lab:6443/livez)" = ok ] && echo "API viva (curl)"
