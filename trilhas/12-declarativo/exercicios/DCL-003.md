# DCL-003 — create × apply: criar uma vez ou declarar sempre

## Identificação

- **ID:** DCL-003
- **Trilha:** [12 — Manifestos declarativos](../README.md)
- **Referência didática:** DO180/DO280 — gerenciamento declarativo.
- **Fichas de comando:** [`oc-apply-patch-diff`](../../../catalogo/fichas/oc-apply-patch-diff.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Aplicar a aplicação completa com `oc apply -f`, comparar com `oc create -f` e ler a anotação `last-applied-configuration`.

**Indicador de sucesso:** a aplicação responde pela Route; um segundo `oc apply` diz `unchanged`; `oc create` do mesmo arquivo falha com `AlreadyExists`.

## Conceito

> **Arquivo de trabalho.** Os exercícios editam a cópia `/tmp/ac12/app.yaml`, nunca o manifesto do repositório.
> Para recomeçar: `cp manifests/apps-exemplo/declarativo-app.yaml /tmp/ac12/app.yaml`.

| | `oc create -f` | `oc apply -f` |
|---|---|---|
| Objeto não existe | cria | cria |
| Objeto existe | erro `AlreadyExists` | mescla as diferenças |
| Repetível | não | sim (idempotente) |
| Guarda o que você declarou | não | sim: anotação `kubectl.kubernetes.io/last-applied-configuration` |

A anotação é a "memória" do `apply` para saber o que **você** declarou da última vez (base do merge de três vias, DCL-005).

## Comandos guiados

```bash
mkdir -p /tmp/ac12 && cp manifests/apps-exemplo/declarativo-app.yaml /tmp/ac12/app.yaml
oc apply -f /tmp/ac12/app.yaml -n ac12-declarativo
oc rollout status deployment/ac12-web -n ac12-declarativo
oc apply -f /tmp/ac12/app.yaml -n ac12-declarativo                    # unchanged
oc create -f /tmp/ac12/app.yaml -n ac12-declarativo; echo "rc=$?"     # AlreadyExists
oc apply view-last-applied deployment/ac12-web -n ac12-declarativo | head -15
oc get deployment ac12-web -n ac12-declarativo -o jsonpath='{.metadata.annotations}' | jq 'keys'
H=$(oc get route ac12-web -n ac12-declarativo -o jsonpath='{.spec.host}'); curl -sSk "https://$H/" 2>/dev/null || curl -sS "http://$H/"
```

## Repetições

1. Apague só o Service e rode `oc apply` de novo: o que muda na saída?
2. Crie um ConfigMap com `oc create configmap` (imperativo) e depois `oc apply` de um YAML dele: o aviso que aparece fala de quê?
3. `oc apply -f ... -o name` e `--dry-run=server -o yaml | head`.
4. Use `oc apply set-last-applied` para "adotar" um objeto criado imperativamente (`--create-annotation`).
5. Por que `oc create -f` ainda é útil? (ex.: `generateName`, recursos que nunca devem ser atualizados)

## Desafio sem pista

Mostre a diferença entre o que você declarou (`last-applied`) e o objeto real no cluster para o Deployment: liste os
campos que existem no real mas não no declarado (defaults do servidor).

## Diagnóstico controlado

- **Sintoma:** `Warning: resource configmaps/... is missing the kubectl.kubernetes.io/last-applied-configuration annotation which is required by oc apply`.
- **Hipóteses:** objeto criado com `create` e agora gerenciado com `apply`.
- **Investigação:** `oc get cm <nome> -o jsonpath='{.metadata.annotations}'`.
- **Reversão:** nada a reverter; o `apply` grava a anotação. Daqui em diante, use só `apply` nesse objeto.

## Validação

```bash
oc apply -f /tmp/ac12/app.yaml -n ac12-declarativo | grep -c unchanged    # 4
```
