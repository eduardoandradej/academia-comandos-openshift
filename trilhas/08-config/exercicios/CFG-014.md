# CFG-014 — Quem pode ler seus Secrets

## Identificação

- **ID:** CFG-014
- **Trilha:** [08 — ConfigMaps e Secrets](../README.md)
- **Referência didática:** DO280 — RBAC e proteção de dados sensíveis.
- **Fichas de comando:** [`oc-auth-can-i`](../../../catalogo/fichas/oc-auth-can-i.md), [`oc-configmap-secret`](../../../catalogo/fichas/oc-configmap-secret.md)

## Objetivo e indicador de sucesso

Verificar quem pode ler Secrets no projeto, entender por que o papel `view` não os lê e onde os valores ainda podem vazar.

**Indicador de sucesso:** você lista três caminhos pelos quais um valor de Secret pode vazar mesmo sem `get secrets`.

**Nível:** Intermediário

## Conceito

| Papel no projeto | Lê Secrets? |
|---|---|
| `view` | **não** |
| `edit` | sim |
| `admin` | sim |

Caminhos de vazamento que o RBAC de Secrets não cobre: `oc exec ... env` (quem pode fazer exec), logs da aplicação
que imprimem variáveis, e quem pode criar pods no projeto (pode montar qualquer Secret do namespace). No cluster, a
criptografia do etcd em repouso é configuração do admin (somente leitura aqui).

## Comandos guiados

```bash
oc auth can-i get secrets -n ac08-config
oc auth can-i create pods/exec -n ac08-config
ac-admin
oc adm policy who-can get secrets -n ac08-config | head -20
oc auth can-i get secrets -n ac08-config --as=system:serviceaccount:ac08-config:default    # a SA padrão lê?
oc get apiserver cluster -o jsonpath='{.spec.encryption.type}{"\n"}'                        # vazio = sem criptografia do etcd configurada
ac-dev
oc exec deploy/ac08-app -n ac08-config -- sh -c 'printenv | grep -c "^DB_"'               # quem tem exec vê as variáveis
```

## Repetições

1. (admin) Conceda `view` a `developer` em um projeto rascunho e teste `oc get secrets` lá; remova em seguida.
2. Liste os papéis (`rolebindings`) do `ac08-config`.
3. Por que montar Secrets como arquivo com `defaultMode` restrito não protege de quem tem `exec`?
4. Leia a seção de criptografia do etcd na documentação da sua versão (conceitual).
5. Liste os Secrets que o próprio OpenShift criou no projeto (tokens, pull secrets) só por nome e tipo.

## Desafio sem pista

Mostre, como admin e só com leitura/permissões temporárias, que um usuário com `view` em um projeto rascunho consegue
listar ConfigMaps mas recebe `Forbidden` ao ler Secrets. Remova tudo ao final.

## Diagnóstico controlado

- **Sintoma:** um colega com papel `view` diz "não consigo ver o Secret, o cluster está quebrado".
- **Hipóteses:** comportamento correto do papel `view`.
- **Investigação:** `oc auth can-i get secrets -n <ns> --as=<usuário>`.
- **Reversão:** nada a reverter; se ele precisar, avalie `edit` ou um papel próprio só com `get` naquele Secret.

## Validação

```bash
oc auth can-i get secrets -n ac08-config    # yes (developer é admin do projeto)
```
