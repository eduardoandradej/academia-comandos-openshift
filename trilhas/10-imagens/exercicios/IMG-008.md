# IMG-008 — Gatilho de imagem: atualizar o Deployment quando a tag muda

## Identificação

- **ID:** IMG-008
- **Trilha:** [10 — Imagens e registries](../README.md)
- **Referência didática:** DO180/DO280 — ImageStreams e triggers.
- **Fichas de comando:** [`oc-image-imagestream`](../../../catalogo/fichas/oc-image-imagestream.md), [`oc-rollout`](../../../catalogo/fichas/oc-rollout.md)

## Objetivo e indicador de sucesso

Ligar um gatilho de imagem (`oc set triggers --from-image`) para que mover a tag `prod` gere um rollout sozinho.

**Indicador de sucesso:** `oc tag ... ac10-web:prod` cria uma nova revisão do `ac10-app` sem nenhum comando no Deployment.

## Conceito

`oc set triggers deployment/X --from-image=IS:tag --containers=C` grava a anotação `image.openshift.io/triggers`.
Um controlador observa a istag e, quando o digest muda, **escreve o digest novo** no template do contêiner `C` —
o que dispara um rollout normal (com histórico e `rollout undo`).

Fluxo de promoção completo: importar/testar em `v2` → `oc tag ac10-web:v2 ac10-web:prod` → rollout automático.

## Comandos guiados

```bash
C=$(oc get deployment ac10-app -n ac10-imagens -o jsonpath='{.spec.template.spec.containers[0].name}')
oc set triggers deployment/ac10-app --from-image=ac10-web:prod --containers="$C" -n ac10-imagens
oc set triggers deployment/ac10-app -n ac10-imagens                         # lista os gatilhos
oc get deployment ac10-app -n ac10-imagens -o jsonpath='{.metadata.annotations.image\.openshift\.io/triggers}{"\n"}'
oc import-image ac10-web:v2 --from=registry.access.redhat.com/ubi8/httpd-24:latest --confirm -n ac10-imagens
oc rollout history deployment/ac10-app -n ac10-imagens | tail -3
oc tag ac10-web:v2 ac10-web:prod -n ac10-imagens                            # promoção
oc rollout status deployment/ac10-app -n ac10-imagens
oc rollout history deployment/ac10-app -n ac10-imagens | tail -3            # revisão nova
oc exec deploy/ac10-app -n ac10-imagens -- cat /etc/redhat-release          # Red Hat Enterprise Linux 8.x
```

## Repetições

1. Volte a `prod` para `v1` e observe o rollout automático (e o `release` 9.x).
2. Use `oc rollout undo` em vez de mover a tag: o que acontece com o gatilho na próxima mudança?
3. Pause o gatilho: `oc set triggers deployment/ac10-app --from-image=ac10-web:prod --containers="$C" --manual`.
4. Remova todos os gatilhos (`oc set triggers deployment/ac10-app --remove-all`).
5. Leia a anotação de gatilhos e explique o campo `fieldPath`.

## Desafio sem pista

Monte o fluxo de promoção "v1 → prod" em um único comando seguro: só promove se a tag de origem existir e for
diferente da `prod`, e espera o rollout terminar.

## Diagnóstico controlado

- **Sintoma:** a tag `prod` mudou, mas o Deployment não criou revisão.
- **Hipóteses:** (a) gatilho ausente/pausado (`paused: true`); (b) nome do contêiner errado no gatilho; (c) o digest não mudou de fato.
- **Investigação:** `oc set triggers deployment/ac10-app`; anotação de gatilhos; digests das istags.
- **Reversão:** corrija o gatilho com `--containers=<nome certo>`. Veja TS-032.

## Validação

```bash
oc set triggers deployment/ac10-app -n ac10-imagens | grep -q 'ac10-web:prod' && echo "gatilho ativo"
```

## Limpeza segura

```bash
oc tag ac10-web:v1 ac10-web:prod -n ac10-imagens
```
