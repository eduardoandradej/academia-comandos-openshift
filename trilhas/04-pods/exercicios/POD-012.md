## Objetivo e indicador de sucesso

Criar pods nas três classes de QoS (`BestEffort`, `Burstable`, `Guaranteed`) e ver o efeito da quota e do LimitRange do projeto.

**Indicador de sucesso:** três pods com a classe de QoS que você previu, e a explicação de por que o LimitRange pode mudar a classe.

## Conceito

| QoS | Regra | Prioridade de despejo sob pressão |
|---|---|---|
| `Guaranteed` | todo contêiner com requests = limits de CPU **e** memória | última |
| `Burstable` | ao menos um request ou limit, sem ser Guaranteed | intermediária |
| `BestEffort` | nenhum request nem limit | primeira |

Se o projeto tiver o LimitRange da Academia (`ac-limits`), contêineres sem recursos **recebem os padrões** — e o pod
deixa de ser `BestEffort`. Requests e limits de pods existentes não se editam: recrie o pod (ou use um Deployment).

## Comandos guiados

```bash
oc get limitrange,resourcequota -n ac04-pods              # há baseline? (opcional: aplicar como admin, ORI-012)
for q in best burst guar; do
  case $q in
    best)  R='' ;;
    burst) R='"resources":{"requests":{"cpu":"10m","memory":"16Mi"},"limits":{"memory":"64Mi"}},' ;;
    guar)  R='"resources":{"requests":{"cpu":"20m","memory":"32Mi"},"limits":{"cpu":"20m","memory":"32Mi"}},' ;;
  esac
  oc run "ac04-qos-$q" --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac04-pods \
    --labels=academy.openshift.dev/managed-by=academia --restart=Never \
    --overrides="{\"spec\":{\"containers\":[{\"name\":\"ac04-qos-$q\",\"image\":\"registry.access.redhat.com/ubi9/httpd-24:latest\",${R}\"command\":[\"sleep\",\"600\"]}]}}"
done
oc get pods -n ac04-pods -l academy.openshift.dev/managed-by=academia \
  -o custom-columns=NOME:.metadata.name,QOS:.status.qosClass,REQ:.spec.containers[0].resources.requests,LIM:.spec.containers[0].resources.limits
oc describe resourcequota -n ac04-pods 2>/dev/null | head -20
```

## Repetições

1. Sem baseline, `ac04-qos-best` fica `BestEffort`; com baseline, qual classe ele recebe? (Peça ao admin aplicar e recrie.)
2. Tente `oc set resources pod/ac04-qos-best --limits=memory=64Mi -n ac04-pods` e leia o erro.
3. Com baseline aplicada, tente criar um pod com `limits.memory: 1Gi` e leia a recusa do LimitRange.
4. `oc adm top pods -n ac04-pods` (se as métricas estiverem disponíveis) e compare uso × requests.
5. Gere o YAML do Guaranteed com `--dry-run=client -o yaml` e guarde como referência.

## Desafio sem pista

Faça um pod de **dois** contêineres que seja `Guaranteed` e um de dois contêineres que seja `Burstable` por causa de
apenas um campo. Prove a classe de cada um.

## Diagnóstico controlado

- **Sintoma:** `forbidden: maximum memory usage per Container is 512Mi, but limit is 1Gi` ao criar um pod.
- **Hipóteses:** LimitRange `ac-limits` com `max`.
- **Investigação:** `oc describe limitrange ac-limits -n ac04-pods`.
- **Reversão:** nada foi criado; ajuste os limites para dentro do máximo.

## Validação

```bash
oc get pod ac04-qos-guar -n ac04-pods -o jsonpath='{.status.qosClass}{"\n"}'   # Guaranteed
```
