# STO-008 — Primeiro PVC: dados que sobrevivem ao pod

## Identificação

- **ID:** STO-008
- **Trilha:** [09 — Storage](../README.md)
- **Referência didática:** DO180 — armazenamento persistente.
- **Fichas de comando:** [`oc-pvc-storage`](../../../catalogo/fichas/oc-pvc-storage.md), [`oc-set-volume`](../../../catalogo/fichas/oc-set-volume.md)

## Objetivo e indicador de sucesso

Criar um PVC, montá-lo em um Deployment e provar que os dados sobrevivem à remoção do pod e a um `rollout restart`.

**Indicador de sucesso:** o arquivo `/dados/marca.txt` continua lá depois de dois pods diferentes.

**REQUER PREPARAÇÃO** — feita uma vez, pelo admin, conforme [docs/10-preparacao-storage.md](../../../docs/10-preparacao-storage.md):
PVs estáticos por NFS (opção A) ou LVM Storage (opção B), e a quota do `ac09-storage` liberando PVCs.

```bash
export SC=ac09-nfs        # opção A; na opção B: export SC=lvms-vg1
oc get resourcequota -n ac09-storage -o jsonpath='{range .items[*]}{.metadata.name}{": pvc="}{.spec.hard.persistentvolumeclaims}{" storage="}{.spec.hard.requests\.storage}{"\n"}{end}'
# esperado: pvc >= 3 e storage >= 3Gi; "pvc=0" significa que a preparação não foi feita
```

Sem a preparação, leia o exercício e faça só as partes de leitura e `--dry-run=client`.

## Conceito

Fluxo: o PVC pede → o cluster liga (`Bound`) a um PV que atende (estático) ou cria um (dinâmico) → o pod monta o PVC.
O PVC é do projeto e vive independente dos pods: apagar o Deployment não apaga os dados.

Algumas classes só ligam o PVC quando um pod o usa (`volumeBindingMode: WaitForFirstConsumer`, comum no LVMS):
o PVC fica `Pending` até existir o pod — isso é normal.

## Comandos guiados

```bash
oc apply -n ac09-storage -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ac09-dados
  labels:
    academy.openshift.dev/managed-by: academia
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: ${SC}
  resources:
    requests:
      storage: 500Mi
EOF
oc get pvc ac09-dados -n ac09-storage
oc set volume deployment/ac09-app --add --name=dados --type=pvc --claim-name=ac09-dados --mount-path=/dados -n ac09-storage
oc rollout status deployment/ac09-app -n ac09-storage
oc get pvc ac09-dados -n ac09-storage -o jsonpath='{.status.phase} {.spec.volumeName} {.status.capacity.storage}{"\n"}'
oc exec deploy/ac09-app -n ac09-storage -- sh -c 'date > /dados/marca.txt; id; ls -ln /dados'
oc delete pod -n ac09-storage -l app=ac09-app --wait=true
oc rollout status deployment/ac09-app -n ac09-storage
oc exec deploy/ac09-app -n ac09-storage -- cat /dados/marca.txt          # mesmo conteúdo, pod novo
oc describe pvc ac09-dados -n ac09-storage | sed -n '1,20p'
```

## Repetições

1. Faça `rollout restart` e confira o arquivo de novo.
2. `oc get pvc -n ac09-storage -o wide` e `oc describe pvc` — encontre `Used By`.
3. Apague o Deployment, recrie-o e remonte o mesmo PVC: os dados voltaram?
4. Compare o tamanho pedido com `status.capacity` (num PV estático de 1Gi, o PVC recebe 1Gi).
5. (admin) `oc get pv <spec.volumeName> -o yaml | grep -A5 claimRef`.

## Desafio sem pista

Prove que o dado está no **armazenamento** e não no pod: grave um arquivo, apague o Deployment inteiro, crie um pod
solto que monte o mesmo PVC e leia o arquivo.

## Diagnóstico controlado

- **Sintoma:** `touch: cannot touch '/dados/marca.txt': Permission denied`.
- **Hipóteses:** (a) opção A: diretório NFS sem permissão para o UID arbitrário (veja a preparação: `all_squash` e modo 0777); (b) volume montado somente leitura.
- **Investigação:** `oc exec ... -- sh -c 'id; ls -ldn /dados; mount | grep /dados'`.
- **Reversão:** corrija as permissões no servidor NFS (tarefa do admin no host) — nunca peça SCC `anyuid` para "resolver".

## Validação

```bash
oc get pvc ac09-dados -n ac09-storage -o jsonpath='{.status.phase}{"\n"}'     # Bound
oc exec deploy/ac09-app -n ac09-storage -- test -s /dados/marca.txt && echo OK
```
