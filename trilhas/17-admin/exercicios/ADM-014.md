## Objetivo e indicador de sucesso

Classificar "o pod não sobe" pela camada de recursos: quota, LimitRange, prioridade, agendamento (reserva do nó) ou
pressão no nó (despejo).

**Indicador de sucesso:** quatro falhas provocadas no `ac17-cotas` classificadas na camada certa pela mensagem.

## Conceito

| Camada | Onde aparece | Mensagem típica |
|---|---|---|
| quota | erro do `oc`/evento do RS | `exceeded quota`, `must specify` |
| LimitRange | erro do `oc`/evento do RS | `maximum ... per Container`, `minimum`, `ratio` |
| prioridade | erro do `oc` | `no PriorityClass with name` |
| agendamento | pod `Pending`, `FailedScheduling` | `Insufficient cpu`, `didn't match node selector` |
| pressão no nó | pod `Evicted` | `The node was low on resource: memory` |

## Comandos guiados

```bash
ac-dev
oc create deployment ac17-grande --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac17-cotas --dry-run=client -o yaml \
  | oc set resources --local -f - --requests=cpu=200m,memory=200Mi --limits=cpu=250m,memory=256Mi -o yaml | oc apply -n ac17-cotas -f -
oc scale deployment/ac17-grande --replicas=2 -n ac17-cotas
sleep 10; oc get events -n ac17-cotas --field-selector type=Warning --sort-by=.lastTimestamp | tail -3      # quota
oc run ac17-lr --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac17-cotas --overrides='{"spec":{"containers":[{"name":"ac17-lr","image":"registry.access.redhat.com/ubi9/httpd-24:latest","resources":{"limits":{"cpu":"400m"}}}]}}' 2>&1 | tail -1   # LimitRange
oc run ac17-pc --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac17-cotas --overrides='{"spec":{"priorityClassName":"ac17-alta"}}' 2>&1 | tail -1                  # prioridade
oc run ac17-ns --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac17-cotas --overrides='{"spec":{"nodeSelector":{"disco":"inexistente"}}}'; sleep 5
oc get pod ac17-ns -n ac17-cotas -o jsonpath='{.status.conditions[0].message}{"\n"}'                                         # agendamento
ac-admin
```

## Repetições

1. Classifique cada falha pela tabela.
2. Quais falhas impedem o pod de existir e quais deixam o pod `Pending`?
3. (admin) As condições do nó estão normais? (`MemoryPressure`, `DiskPressure`, `PIDPressure`)
4. Corrija cada falha com a menor mudança.
5. Escreva a tabela de memória.

## Desafio sem pista

Escreva `por_que_nao_sobe <deployment>` que olha os eventos do ReplicaSet e dos pods do Deployment e imprime a camada (quota, LimitRange, prioridade, agendamento ou despejo).

## Diagnóstico controlado

- **Sintoma:** Deployment com `READY 1/2`, sem pod `Pending` visível.
- **Hipóteses:** o segundo pod nem foi criado (recusa de admissão: quota/LimitRange); o erro está no ReplicaSet.
- **Investigação:** `oc describe rs -l app=<nome>` (Events).
- **Reversão:** ajuste requests ou réplicas.

## Validação

```bash
oc get pod ac17-ns -n ac17-cotas -o jsonpath='{.status.phase}{"\n"}'     # Pending
```

oc delete deployment ac17-grande -n ac17-cotas --ignore-not-found
