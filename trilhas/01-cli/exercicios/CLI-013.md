## Conceito

O `kubectl` fala com qualquer API Kubernetes, inclusive os tipos do OpenShift (Routes, Projects), porque eles são
recursos de API. O `oc` acrescenta **comandos de fluxo** do OpenShift: `login`, `logout`, `project`, `new-project`,
`new-app`, `start-build`, `adm`, `policy`...

Ambos leem o mesmo kubeconfig. Na prática da Academia: use `oc`; use `kubectl` para treinar a portabilidade.

## Comandos guiados

```bash
oc get pods -n ac01-cli && kubectl get pods -n ac01-cli
oc get routes -n ac01-cli && kubectl get routes -n ac01-cli         # Routes são recursos de API
kubectl config current-context && oc config current-context
kubectl auth whoami                                                 # equivalente a oc auth whoami
kubectl config set-context --current --namespace=ac01-cli          # equivalente a parte do 'oc project'
kubectl get projects                                                # funciona: é um recurso de API
kubectl api-resources --api-group=route.openshift.io
```

## Desafio sem pista

Escolha dois comandos do `oc` sem equivalente direto no `kubectl` e descreva qual sequência de comandos `kubectl`
(ou de API) chega ao mesmo resultado — ou por que não chega.

## Diagnóstico controlado

- **Sintoma:** `kubectl login` → `error: unknown command "login" for "kubectl"`.
- **Hipóteses:** comando exclusivo do `oc`.
- **Investigação:** `kubectl --help | grep -i login`; `oc login --help | head -5`.
- **Reversão:** nada a reverter.

## Validação

```bash
diff <(oc get pods -n ac01-cli -o name) <(kubectl get pods -n ac01-cli -o name) && echo "mesma visão"
```
