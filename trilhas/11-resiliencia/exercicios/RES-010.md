# RES-010 — Rollout sem indisponibilidade

## Identificação

- **ID:** RES-010
- **Trilha:** [11 — Resiliência](../README.md)
- **Referência didática:** DO180/DO280 — estratégias de implantação e disponibilidade.
- **Fichas de comando:** [`oc-set-probe-autoscale`](../../../catalogo/fichas/oc-set-probe-autoscale.md), [`oc-rollout`](../../../catalogo/fichas/oc-rollout.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Fazer um rollout com 2 réplicas sem nenhuma requisição recusada, combinando readiness, `maxUnavailable: 0`,
`maxSurge: 1` e `preStop` — e mostrar a diferença sem eles.

**Indicador de sucesso:** o contador de falhas do cliente fica em 0 durante o rollout configurado, e > 0 no rollout "ruim".

## Conceito

| Ingrediente | Por que |
|---|---|
| readiness probe | o pod novo só recebe tráfego quando responde |
| `maxUnavailable: 0` | nunca há menos réplicas prontas que o desejado |
| `maxSurge: 1` | sobe um pod novo antes de tirar um antigo (precisa de folga na quota) |
| `preStop` curto | o pod antigo sai dos endpoints antes de parar |

O cliente de teste roda **dentro** do cluster (sem `curl` na imagem: `/dev/tcp`, como na Trilha 06).

## Comandos guiados

```bash
oc scale deployment/ac11-app --replicas=2 -n ac11-resiliencia
oc patch deployment ac11-app -n ac11-resiliencia --type=merge -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxUnavailable":0,"maxSurge":1}}}}'
oc rollout status deployment/ac11-app -n ac11-resiliencia
oc run ac11-cliente --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac11-resiliencia \
  --labels=academy.openshift.dev/managed-by=academia --command -- sleep 3600
oc wait --for=condition=Ready pod/ac11-cliente -n ac11-resiliencia --timeout=60s
oc exec ac11-cliente -n ac11-resiliencia -- bash -c 'ok=0; f=0; end=$((SECONDS+60)); while [ $SECONDS -lt $end ]; do
  if timeout 2 bash -c "exec 3<>/dev/tcp/ac11-app/8080 && printf \"GET / HTTP/1.0\r\n\r\n\" >&3 && head -1 <&3" >/dev/null 2>&1; then ok=$((ok+1)); else f=$((f+1)); fi; sleep 0.2
done; echo "ok=$ok falhas=$f"' &
sleep 5; oc rollout restart deployment/ac11-app -n ac11-resiliencia; oc rollout status deployment/ac11-app -n ac11-resiliencia
wait                                                                              # ok=... falhas=0
```

## Repetições

1. Faça o rollout "ruim": `maxUnavailable: 1`, `maxSurge: 0`, sem readiness e sem `preStop`. Conte as falhas.
2. Mude só uma coisa por vez e descubra qual ingrediente mais pesa.
3. Durante o rollout, observe `oc get pods -w`: quantos pods existem no pico?
4. Por que `maxSurge` exige folga na quota?
5. Com `strategy: Recreate`, quantas falhas? (esperado: muitas)

## Desafio sem pista

Produza uma tabela com o número de falhas em três configurações (completa, sem `preStop`, sem readiness) e explique
cada resultado.

## Diagnóstico controlado

- **Sintoma:** algumas requisições recusadas a cada deploy, mesmo com readiness.
- **Hipóteses:** sem `preStop`, o pod antigo para antes de sair de todos os balanceadores; `maxUnavailable` > 0.
- **Investigação:** estratégia do Deployment; `lifecycle` do contêiner; contador do cliente.
- **Reversão:** acrescente o ingrediente que falta.

## Validação

```bash
oc get deployment ac11-app -n ac11-resiliencia -o jsonpath='{.spec.strategy.rollingUpdate.maxUnavailable}{"\n"}'   # 0
```
