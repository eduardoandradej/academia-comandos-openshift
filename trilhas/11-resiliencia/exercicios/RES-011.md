# RES-011 — HPA: escalar por CPU (até 2 réplicas)

## Identificação

- **ID:** RES-011
- **Trilha:** [11 — Resiliência](../README.md)
- **Referência didática:** DO180/DO280 — escalonamento automático.
- **Fichas de comando:** [`oc-set-probe-autoscale`](../../../catalogo/fichas/oc-set-probe-autoscale.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Criar um HorizontalPodAutoscaler com `oc autoscale`, gerar carga controlada e ver o HPA subir de 1 para 2 réplicas e voltar.

**Indicador de sucesso:** `oc get hpa` mostra `TARGETS` acima de 50% e `REPLICAS 2`; depois da carga, volta a 1.

## Nível

**Nível:** Avançado

## Duração e repetições

- **Duração sugerida:** 20 min
- **Repetições:** 3×

## Contexto

- **Terminal:** `student@ocp-admin`, na raiz do repositório clonado (`cd ~/academia-comandos-openshift`)
- **Perfil:** `developer`
- **Projeto:** `ac11-resiliencia`
- **Impacto:** MUTAÇÃO LOCAL REVERSÍVEL (carga de 0,1 vCPU por pod, máximo 2 pods)

```bash
source scripts/perfis.sh && ac-dev   # perfil developer (ORI-004)

```


REQUER PREPARAÇÃO: pull de `registry.access.redhat.com/ubi9/httpd-24` (normalmente já em cache).

**Depende da Metrics API.** Confira antes:


Se a Metrics API não responder, faça o exercício só até a criação do HPA e leia a condição `ScalingActive`.

## Conceito

> **Carga controlada.** Os testes de CPU usam um laço dentro de contêineres com `limits.cpu: 100m`: cada pod consome
> no máximo 0,1 vCPU, e o HPA está limitado a 2 réplicas. Não aumente esses valores no SNO.

O HPA compara o uso médio de CPU com o **request** (`--cpu-percent=50` → alvo de 25m para request de 50m) e calcula
`réplicas = ceil(atual × uso/alvo)`, entre `--min` e `--max`. Sem `requests.cpu`, o alvo fica `<unknown>` (TS-035).
Subir é rápido; descer espera uma janela de estabilização (padrão 5 min).

## Comandos guiados

```bash
oc get deployment ac11-app -n ac11-resiliencia -o jsonpath='{.spec.template.spec.containers[0].resources.requests.cpu}{"\n"}'   # 50m
oc autoscale deployment/ac11-app --min=1 --max=2 --cpu-percent=50 -n ac11-resiliencia
oc label hpa ac11-app academy.openshift.dev/managed-by=academia -n ac11-resiliencia
sleep 30; oc get hpa ac11-app -n ac11-resiliencia
oc exec deploy/ac11-app -n ac11-resiliencia -- timeout 180 sh -c 'while :; do :; done' &
for i in $(seq 8); do sleep 20; oc get hpa ac11-app -n ac11-resiliencia --no-headers; done
wait
oc describe hpa ac11-app -n ac11-resiliencia | sed -n '/Conditions:/,$p'
```

## Repetições

1. Calcule o número de réplicas que o HPA quereria com 100m de uso e alvo 25m (e por que fica em 2).
2. Acompanhe a descida depois da carga: quanto tempo levou?
3. `oc get hpa ac11-app -o yaml` — encontre `metrics`, `currentMetrics` e `conditions`.
4. Tente `oc scale --replicas=1` com o HPA ativo e a carga rodando: quem vence?
5. Por que a Academia limita o `--max` a 2?

## Desafio sem pista

Faça a descida acontecer em ~1 minuto (em vez de 5) ajustando o `behavior` do HPA, e prove medindo.

## Diagnóstico controlado

- **Sintoma:** `TARGETS <unknown>/50%` e condição `FailedGetResourceMetric`.
- **Hipóteses:** (a) sem `requests.cpu`; (b) Metrics API indisponível; (c) pods ainda iniciando.
- **Investigação:** requests do contêiner; `oc adm top pods`; `oc describe hpa` (Conditions/Events).
- **Reversão:** defina `requests.cpu` (RES-001) ou aguarde as métricas. Veja TS-035.

## Validação

```bash
oc get hpa ac11-app -n ac11-resiliencia -o jsonpath='{.spec.minReplicas}-{.spec.maxReplicas}{"\n"}'    # 1-2
```

## Limpeza segura

```bash
oc exec deploy/ac11-app -n ac11-resiliencia -- pkill -f 'while :' 2>/dev/null || true
```

O HPA fica para o RES-012.
