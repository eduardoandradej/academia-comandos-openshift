# RES-006 — Startup probe: proteger aplicações lentas para iniciar

## Identificação

- **ID:** RES-006
- **Trilha:** [11 — Resiliência](../README.md)
- **Referência didática:** DO180/DO280 — saúde de aplicações (startup).
- **Fichas de comando:** [`oc-set-probe-autoscale`](../../../catalogo/fichas/oc-set-probe-autoscale.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Simular uma aplicação que demora a iniciar e usar uma startup probe para que a liveness não a mate durante a subida.

**Indicador de sucesso:** sem startup probe, o pod entra em ciclo de reinícios; com ela, sobe com `RESTARTS 0`.

## Conceito

Enquanto a startup probe não passa, liveness e readiness ficam suspensas. Ela tolera `failureThreshold ×
periodSeconds` segundos de inicialização (ex.: 30 × 2 s = 60 s). Depois que passa uma vez, não roda mais.
Alternativa ruim: `initialDelaySeconds` enorme na liveness, que atrasa a detecção de travamentos para sempre.

## Comandos guiados

```bash
oc create deployment ac11-lento --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac11-resiliencia -- sh -c 'sleep 25; exec run-httpd'
oc label deployment ac11-lento academy.openshift.dev/managed-by=academia -n ac11-resiliencia
oc set resources deployment/ac11-lento --requests=cpu=20m,memory=48Mi --limits=cpu=100m,memory=128Mi -n ac11-resiliencia
oc set probe deployment/ac11-lento --liveness --open-tcp=8080 --period-seconds=5 --failure-threshold=2 -n ac11-resiliencia
sleep 60; oc get pods -n ac11-resiliencia -l app=ac11-lento                  # reinícios: morre antes de subir
oc set probe deployment/ac11-lento --startup --open-tcp=8080 --period-seconds=2 --failure-threshold=30 -n ac11-resiliencia
oc rollout status deployment/ac11-lento -n ac11-resiliencia --timeout=120s
oc get pods -n ac11-resiliencia -l app=ac11-lento                            # 1/1, RESTARTS 0
```

## Repetições

1. Calcule a tolerância da startup probe configurada.
2. Aumente o `sleep` para 90 s (sem mudar a probe) e veja o que acontece.
3. Leia as três probes do contêiner no YAML.
4. Por que não basta `--initial-delay-seconds=30` na liveness?
5. Remova a startup probe e recoloque de memória.

## Desafio sem pista

Ajuste a startup probe para tolerar exatamente até 40 s de inicialização, com verificação a cada 4 s, e prove que um
`sleep 25` passa e um `sleep 50` reinicia.

## Diagnóstico controlado

- **Sintoma:** `CrashLoopBackOff` em uma aplicação que "funciona na máquina do desenvolvedor"; eventos `Liveness probe failed` logo após iniciar.
- **Hipóteses:** a liveness começa a avaliar antes de a aplicação abrir a porta.
- **Investigação:** tempo de inicialização nos logs (`oc logs --previous`); `initialDelaySeconds` e probes do contêiner.
- **Reversão:** acrescente startup probe com tolerância medida.
