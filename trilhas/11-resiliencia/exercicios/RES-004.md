# RES-004 — Readiness probe: tirar do Service quem não está pronto

## Identificação

- **ID:** RES-004
- **Trilha:** [11 — Resiliência](../README.md)
- **Referência didática:** DO180 — saúde de aplicações (probes).
- **Fichas de comando:** [`oc-set-probe-autoscale`](../../../catalogo/fichas/oc-set-probe-autoscale.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Configurar uma readiness probe com `oc set probe`, ver um pod `Running` mas `0/1` sair dos endpoints e corrigir a probe.

**Indicador de sucesso:** com a probe HTTP em `/` (403 na UBI) o pod nunca fica pronto; com `--open-tcp=8080`, fica.

## Conceito

| Probe | Pergunta | Ao falhar |
|---|---|---|
| readiness | "posso receber tráfego?" | sai dos endpoints do Service; **não** reinicia |
| liveness | "estou vivo?" | o contêiner é **reiniciado** (RES-005) |
| startup | "já terminei de iniciar?" | segura as outras até passar; reinicia se nunca passar (RES-006) |

Tipos: `--get-url=http://:PORTA/caminho` (sucesso = HTTP 200–399), `--open-tcp=PORTA`, ou comando (`-- cmd`).
A página padrão do httpd da UBI responde **403** em `/` — uma probe HTTP em `/` falha.

## Comandos guiados

```bash
oc expose deployment/ac11-app --port=8080 -n ac11-resiliencia
oc set probe deployment/ac11-app --readiness --get-url=http://:8080/ --period-seconds=5 -n ac11-resiliencia
sleep 30; oc get pods -n ac11-resiliencia -l app=ac11-app                     # Running 0/1
oc get endpointslices -n ac11-resiliencia -l kubernetes.io/service-name=ac11-app -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]} ready={.conditions.ready}{"\n"}{end}'
oc describe pod -n ac11-resiliencia -l app=ac11-app | grep -E 'Readiness|Unhealthy' | tail -3
oc set probe deployment/ac11-app --readiness --open-tcp=8080 --period-seconds=5 -n ac11-resiliencia
oc rollout status deployment/ac11-app -n ac11-resiliencia
oc get pods -n ac11-resiliencia -l app=ac11-app                               # 1/1
```

## Repetições

1. Leia a probe no YAML (`oc get deploy ac11-app -o jsonpath='{.spec.template.spec.containers[0].readinessProbe}'`).
2. Troque para uma probe por comando: `oc set probe ... --readiness -- test -d /var/www/html`.
3. Remova a probe (`oc set probe deployment/ac11-app --readiness --remove`) e recoloque a TCP.
4. Por que o rollout da probe errada "travou" sem derrubar o pod antigo? (maxUnavailable)
5. Crie um `index.html` via ConfigMap (Trilha 08) e use a probe HTTP em `/`.

## Desafio sem pista

Faça a readiness depender de um arquivo: o pod fica pronto só quando `/tmp/pronto` existe. Prove tirando e
recolocando o pod do Service com `oc exec`.

## Diagnóstico controlado

- **Sintoma:** `Readiness probe failed: HTTP probe failed with statuscode: 403`.
- **Hipóteses:** caminho da probe sem conteúdo (página padrão da UBI responde 403).
- **Investigação:** `oc exec deploy/ac11-app -- bash -c "exec 3<>/dev/tcp/127.0.0.1/8080; printf 'GET / HTTP/1.0\r\n\r\n' >&3; head -1 <&3"`.
- **Reversão:** probe TCP, outro caminho ou conteúdo real em `/`.

## Validação

```bash
oc get deployment ac11-app -n ac11-resiliencia -o jsonpath='{.status.readyReplicas}{"\n"}'    # 1
```
