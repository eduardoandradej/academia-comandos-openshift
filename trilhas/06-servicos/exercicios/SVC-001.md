# SVC-001 — Por que Services existem: IPs de pod mudam

- **ID:** SVC-001

- **Fichas de comando:** [`oc-expose-service`](../../../catalogo/fichas/oc-expose-service.md), [`oc-get`](../../../catalogo/fichas/oc-get.md)

## Objetivo e indicador de sucesso

Implantar os backends `web-azul` e `web-verde` e um pod cliente, provar que IPs de pod mudam e criar o primeiro Service com `oc expose`.

**Indicador de sucesso:** o mesmo nome (`web-azul`) responde antes e depois de o pod ser recriado com outro IP.

## Conceito

Pods são descartáveis: cada recriação ganha um **IP novo**. Um **Service** dá um nome DNS e um IP virtual
(`ClusterIP`) estáveis, e encaminha o tráfego para os pods que casam com o seu **seletor** de rótulos.

```text
cliente ──▶ web-azul:8080 (ClusterIP estável) ──▶ pods com app=loja,cor=azul (IPs que mudam)
```

`oc expose deployment/<nome> --port=8080` cria um Service usando o seletor do próprio Deployment.

## Comandos guiados

```bash
oc new-project ac06-servicos --display-name='Academia 06 - Services'
oc apply -f manifests/apps-exemplo/servicos-azul-verde.yaml -n ac06-servicos
oc run ac06-cliente --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac06-servicos \
  --labels=app=cliente,academy.openshift.dev/managed-by=academia --command -- sleep infinity
oc wait --for=condition=Available deploy/web-azul deploy/web-verde -n ac06-servicos --timeout=180s
oc wait --for=condition=Ready pod/ac06-cliente -n ac06-servicos --timeout=120s
# confira onde o httpd procura as páginas (o manifesto monta a página em /var/www/html):
oc exec deploy/web-azul -n ac06-servicos -- grep -i '^DocumentRoot' /etc/httpd/conf/httpd.conf

http() { oc exec ac06-cliente -n ac06-servicos -- bash -c "exec 3<>/dev/tcp/$1/${2:-8080} && printf 'GET / HTTP/1.0\r\n\r\n' >&3 && cat <&3" | tail -1; }
IP=$(oc get pod -n ac06-servicos -l cor=azul -o jsonpath='{.items[0].status.podIP}'); echo "IP do pod azul: $IP"
http "$IP"                                          # azul (direto no IP do pod)
oc expose deployment/web-azul --port=8080 -n ac06-servicos
oc get svc web-azul -n ac06-servicos
http web-azul                                       # azul (pelo nome do Service)
oc delete pod -n ac06-servicos -l cor=azul          # recria o pod
oc wait --for=condition=Available deploy/web-azul -n ac06-servicos --timeout=120s
oc get pod -n ac06-servicos -l cor=azul -o jsonpath='{.items[0].status.podIP}{"\n"}'   # IP novo
http "$IP" || echo "IP antigo não responde mais"
http web-azul                                       # o nome continua funcionando
```

## Repetições

1. Repita a recriação do pod 5× e anote os IPs: algum se repete?
2. `oc describe svc web-azul -n ac06-servicos` — `Selector`, `IP`, `Port`, `TargetPort`, `Endpoints`.
3. `oc get svc web-azul -n ac06-servicos -o yaml | sed -n '/^spec:/,/^status:/p'`.
4. Exponha `web-verde` também e teste `http web-verde`.
5. Se a página não aparecer (resposta 403 ou vazia), confira o `DocumentRoot` e ajuste o `mountPath` do manifesto.

## Desafio sem pista

Mostre, em uma única sequência, que o `ClusterIP` do Service não muda quando todos os pods do backend são recriados,
enquanto os IPs dos pods mudam.

## Diagnóstico controlado

- **Sintoma:** `http web-azul` retorna a página padrão (`403`) em vez de `azul`.
- **Hipóteses:** (a) o `DocumentRoot` da imagem não é `/var/www/html`; (b) o ConfigMap não foi montado.
- **Investigação:** `oc exec deploy/web-azul -n ac06-servicos -- ls -l /var/www/html`; o `grep DocumentRoot` dos guiados.
- **Reversão:** ajuste o `mountPath` e reaplique o manifesto.

## Validação

```bash
http web-azul    # azul
http web-verde   # verde (após a repetição 4)
```
