## Objetivo e indicador de sucesso

Montar a loja em `ac16-rede`, clientes em `ac16-rede` e `ac16-vizinho`, e provar que, sem NetworkPolicy, todo pod fala com todo pod.

**Indicador de sucesso:** os dois clientes recebem a página da loja pelo nome curto (mesmo projeto) e pelo FQDN (outro projeto).

## Conceito

> **Função de teste `t`** (definida no pré-flight): `t <pod> <projeto> <destino> [porta]` abre uma conexão HTTP de
> dentro do pod (sem `curl`, por `/dev/tcp`) e imprime a última linha da resposta — ou `FALHOU` em 3 s.
> Bloqueio por NetworkPolicy aparece como **timeout** (os pacotes são descartados), não como "connection refused".

Sem nenhuma NetworkPolicy, o OpenShift deixa todo pod alcançar todo pod do cluster (o isolamento entre projetos é
opt-in). A partir do momento em que **uma** política seleciona um pod para um tipo (`Ingress` ou `Egress`), esse
pod passa a aceitar, naquele sentido, só o que alguma política libera.

## Comandos guiados

```bash
oc new-project ac16-rede --display-name='Academia 16 - Rede' >/dev/null 2>&1 || oc project ac16-rede
oc apply -f manifests/apps-exemplo/servicos-azul-verde.yaml -n ac16-rede
oc expose deployment/web-azul --port=8080 -n ac16-rede
oc expose deployment/web-verde --port=8080 -n ac16-rede
oc run ac16-local --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac16-rede \
  --labels=app=ac16-cliente,academy.openshift.dev/managed-by=academia --command -- sleep 86400
oc new-project ac16-vizinho --display-name='Academia 16 - Vizinho' >/dev/null 2>&1 || true
oc run ac16-cliente --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac16-vizinho \
  --labels=app=ac16-cliente,academy.openshift.dev/managed-by=academia --command -- sleep 86400
oc run ac16-intruso --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac16-vizinho \
  --labels=app=intruso,academy.openshift.dev/managed-by=academia --command -- sleep 86400
oc project ac16-rede >/dev/null
oc wait --for=condition=Ready pod -l academy.openshift.dev/managed-by=academia -n ac16-rede --timeout=120s
oc wait --for=condition=Ready pod --all -n ac16-vizinho --timeout=120s
t() { oc exec "$1" -n "$2" -- timeout 3 bash -c "exec 3<>/dev/tcp/$3/${4:-8080} && printf 'GET / HTTP/1.0\r\n\r\n' >&3 && tail -1 <&3" 2>/dev/null || echo FALHOU; }
t ac16-local   ac16-rede    web-azul
t ac16-cliente ac16-vizinho web-azul.ac16-rede.svc.cluster.local
t ac16-intruso ac16-vizinho web-verde.ac16-rede.svc
```

## Repetições

1. Teste também a porta 8443 (`t ... web-azul 8443`): o que volta? (TLS: a última linha é binária ou vazia)
2. Teste direto o IP do pod (`oc get pod -l cor=azul -o wide`), sem o Service.
3. Quais rótulos tem o namespace `ac16-vizinho`? (`kubernetes.io/metadata.name` é automático)
4. Existe alguma NetworkPolicy nos dois projetos?
5. Recrie o laboratório de memória.

## Desafio sem pista

Monte uma matriz origem × destino (3 clientes × `web-azul`, `web-verde`) com o resultado de `t`, como base para comparar depois de cada política.

## Diagnóstico controlado

- **Sintoma:** `t` responde `FALHOU` já no laboratório aberto.
- **Hipóteses:** (a) Service sem endpoints (pods não prontos); (b) nome errado; (c) já existe política no projeto.
- **Investigação:** `oc get endpointslices -n ac16-rede`; `oc get networkpolicy -n ac16-rede`.
- **Reversão:** aguarde os pods ou corrija o nome; remova políticas antigas.
