# NET-009 — Saída só para quem precisa

## Identificação

- **ID:** NET-009
- **Trilha:** [16 — Rede e isolamento](../README.md)
- **Referência didática:** DO280 — NetworkPolicy (egress seletivo).
- **Fichas de comando:** [`oc-networkpolicy`](../../../catalogo/fichas/oc-networkpolicy.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Com saída negada e DNS liberado, permitir que os clientes falem só com a loja (porta 8080) e mais nada — nem com a internet.

**Indicador de sucesso:** `ac16-local` acessa a loja, mas não alcança `registry.access.redhat.com:443`.

## Nível

**Nível:** Intermediário

## Pré-flight

```bash
source scripts/perfis.sh && ac-dev   # perfil developer (ORI-004)
scripts/preflight.sh                 # sem FALHA

```

```bash
oc get pods -n ac16-rede -l app=loja -o name       # web-azul e web-verde (NET-002)
oc get pod ac16-cliente -n ac16-vizinho -o name    # cliente do projeto vizinho (NET-002)
oc get pod ac16-local -n ac16-rede -o name         # cliente do próprio projeto (NET-002)
t() { oc exec "$1" -n "$2" -- timeout 3 bash -c "exec 3<>/dev/tcp/$3/${4:-8080} && printf 'GET / HTTP/1.0\r\n\r\n' >&3 && tail -1 <&3" 2>/dev/null || echo FALHOU; }
t ac16-local ac16-rede web-azul                    # função de teste: imprime a página ou FALHOU
```

REQUER PREPARAÇÃO: pull de `registry.access.redhat.com/ubi9/httpd-24` (normalmente já em cache).

## Conceito

> **Função de teste `t`** (definida no pré-flight): `t <pod> <projeto> <destino> [porta]` abre uma conexão HTTP de
> dentro do pod (sem `curl`, por `/dev/tcp`) e imprime a última linha da resposta — ou `FALHOU` em 3 s.
> Bloqueio por NetworkPolicy aparece como **timeout** (os pacotes são descartados), não como "connection refused".

Para o tráfego **dentro** do projeto passar com saída e entrada controladas, as duas pontas precisam permitir:
a saída do cliente (Egress) e a entrada da loja (Ingress). Destinos fora do cluster são liberados com `ipBlock`
(faixas de IP); nomes DNS não são suportados por NetworkPolicy (o EgressFirewall do OVN, do admin, aceita `dnsName`).

## Comandos guiados

```bash
oc apply -f manifests/networkpolicies/60-permitir-saida-loja.yaml -n ac16-rede
oc get networkpolicy -n ac16-rede
t ac16-local ac16-rede web-azul                                            # azul (saída do cliente + entrada da loja)
oc exec ac16-local -n ac16-rede -- timeout 5 bash -c '</dev/tcp/registry.access.redhat.com/443' && echo "internet ok" || echo "internet FALHOU"
oc exec ac16-local -n ac16-rede -- timeout 5 bash -c '</dev/tcp/kubernetes.default.svc/443' && echo "API ok" || echo "API FALHOU"
```

## Repetições

1. A loja (que não é `app=ac16-cliente`) consegue sair para a internet? Por quê?
2. Libere a saída do cliente para a internet por `ipBlock` (`0.0.0.0/0` com `except` das faixas internas) e teste.
3. Por que a API do cluster ficou inacessível? Quando um pod precisa dela?
4. Remova a `ac16-negar-saida`: o cliente continua restrito? (sim: a `ac16-saida-loja` já o seleciona para Egress)
5. Desenhe as políticas de entrada e saída aplicadas no projeto.

## Desafio sem pista

Libere o `ac16-local` para acessar **só** a porta 443 de `registry.access.redhat.com`, usando `ipBlock` com os IPs
resolvidos agora, e explique por que essa solução é frágil.

## Diagnóstico controlado

- **Sintoma:** com saída liberada no cliente, ele ainda não acessa a loja.
- **Hipóteses:** falta a permissão do outro lado (entrada na loja vinda do cliente).
- **Investigação:** políticas de Ingress que selecionam `app=loja`.
- **Reversão:** libere a entrada correspondente (ex.: `10-permitir-mesmo-projeto.yaml`).

## Validação

```bash
oc exec ac16-local -n ac16-rede -- timeout 5 bash -c '</dev/tcp/registry.access.redhat.com/443' 2>/dev/null || echo "internet bloqueada"
```
