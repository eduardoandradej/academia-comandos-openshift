# NET-007 — Routes depois do isolamento: liberar o router

## Identificação

- **ID:** NET-007
- **Trilha:** [16 — Rede e isolamento](../README.md)
- **Referência didática:** DO280 — NetworkPolicy e Ingress.
- **Fichas de comando:** [`oc-networkpolicy`](../../../catalogo/fichas/oc-networkpolicy.md), [`oc-route`](../../../catalogo/fichas/oc-route.md)
- **Status:** proposto — escrito e revisado estaticamente; ainda não executado contra o cluster pelo autor

## Objetivo e indicador de sucesso

Mostrar que o isolamento derruba as Routes (o router está em outro namespace) e liberar só o router, só na porta 8080.

**Indicador de sucesso:** a Route da loja responde de novo, enquanto o `ac16-intruso` continua bloqueado.

## Conceito

> **Função de teste `t`** (definida no pré-flight): `t <pod> <projeto> <destino> [porta]` abre uma conexão HTTP de
> dentro do pod (sem `curl`, por `/dev/tcp`) e imprime a última linha da resposta — ou `FALHOU` em 3 s.
> Bloqueio por NetworkPolicy aparece como **timeout** (os pacotes são descartados), não como "connection refused".

O router (Ingress Controller) roda em `openshift-ingress`, cujo namespace tem o rótulo
`policy-group.network.openshift.io/ingress: ""`. Uma política de "só o mesmo projeto" bloqueia o router: a Route
responde **503** ou expira. A forma suportada de liberar é selecionar esse rótulo (não o nome do namespace).
O mesmo raciocínio vale para o monitoramento (`openshift-monitoring`), se você expuser métricas.

## Comandos guiados

```bash
oc expose svc/web-azul -n ac16-rede 2>/dev/null || true
H=$(oc get route web-azul -n ac16-rede -o jsonpath='{.spec.host}')
oc get networkpolicy -n ac16-rede
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' "http://$H/"      # 503 ou timeout: router bloqueado
oc apply -f manifests/networkpolicies/30-permitir-router.yaml -n ac16-rede
sleep 3; curl -sS -m 5 "http://$H/"                                  # azul
t ac16-intruso ac16-vizinho web-azul.ac16-rede.svc                   # continua FALHOU
```

## Repetições

1. (admin, leitura) Confira o rótulo: `oc get namespace openshift-ingress --show-labels`.
2. Por que não usar `kubernetes.io/metadata.name: openshift-ingress`? (o rótulo de grupo é a forma suportada e cobre variações)
3. Remova a porta da política do router e teste a 8443 pela Route passthrough (Trilha 07).
4. Aplique a política do router **sem** a de "mesmo projeto": o `ac16-local` acessa?
5. Escreva a política de memória.

## Desafio sem pista

Escreva um teste de uma linha que diga "OK" só se a Route responde **e** o intruso está bloqueado — o "contrato" de rede da loja.

## Diagnóstico controlado

- **Sintoma:** `Application is not available` (503) logo após aplicar políticas, com pods prontos e endpoints corretos.
- **Hipóteses:** o router não alcança os pods (NetworkPolicy).
- **Investigação:** `oc get networkpolicy -n ac16-rede`; existe alguma que libere o grupo de ingress?
- **Reversão:** aplique `30-permitir-router.yaml`. Veja TS-049.

## Validação

```bash
curl -sS -m 5 "http://$(oc get route web-azul -n ac16-rede -o jsonpath='{.spec.host}')/"     # azul
```

## Limpeza segura

Mantenha as políticas de entrada; o NET-008 trata da saída.
