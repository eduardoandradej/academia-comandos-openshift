# TS-060 — Falha intermitente: uma réplica intrusa atrás do Service

- **Trilha:** [19 — Troubleshooting transversal](../../trilhas/19-troubleshooting/README.md)
- **Nível:** Avançado
- **Perfil:** developer
- **Impacto da reprodução:** MUTAÇÃO LOCAL REVERSÍVEL
- **Status:** proposto — ainda não reproduzido contra o cluster pelo autor

## Sintoma

Uma em cada duas ou três requisições ao `ac19-ts060` falha. O Deployment tem 1 réplica saudável. O monitoramento
mostra "tudo pronto".

## Contexto

Projeto `ac19-casos`, com o cliente `ac19-cli`.

## Como reproduzir com segurança

```bash
oc create deployment ac19-ts060 --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac19-casos --port=8080
oc expose deployment ac19-ts060 --port=8080 -n ac19-casos
oc run ac19-ts060-teste --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac19-casos \
  --labels=app=ac19-ts060 --command -- sleep 86400                                     # "pod de teste esquecido"
sleep 20
for i in $(seq 9); do oc exec ac19-cli -n ac19-casos -- timeout 2 bash -c '</dev/tcp/ac19-ts060/8080' 2>/dev/null && echo ok || echo FALHOU; done | sort | uniq -c
```

## Hipóteses a testar

1. Um pod fora do Deployment tem os mesmos rótulos e entra no Service, mas não escuta na 8080.
2. O pod do Deployment reinicia de vez em quando.
3. Rede instável.

## Investigação orientada

- `oc get endpointslices -n ac19-casos -l kubernetes.io/service-name=ac19-ts060 -o jsonpath='{range .items[*].endpoints[*]}{.targetRef.name} {.conditions.ready}{"\n"}{end}'`
- `oc get pods -n ac19-casos -l app=ac19-ts060 -o custom-columns=POD:.metadata.name,DONO:.metadata.ownerReferences[0].kind`
- `oc get pods -n ac19-casos -l app=ac19-ts060 -o wide` (reinícios)

## Critério de resolução

Você encontra o endpoint intruso e explica por que ele está "pronto" sem servir.

## Limpeza

```bash
oc delete deployment,service ac19-ts060 -n ac19-casos --ignore-not-found
oc delete pod ac19-ts060-teste -n ac19-casos --ignore-not-found
```
