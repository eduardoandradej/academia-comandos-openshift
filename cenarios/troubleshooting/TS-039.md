# TS-039 — Conflito de server-side apply entre duas ferramentas

- **Trilha:** [12 — Manifestos declarativos](../../trilhas/12-declarativo/README.md)
- **Nível:** Avançado
- **Perfil:** developer
- **Impacto da reprodução:** MUTAÇÃO LOCAL REVERSÍVEL (ConfigMap de teste)
- **Status:** proposto — ainda não reproduzido contra o cluster pelo autor

## Sintoma

Duas automações aplicam o ConfigMap `ac12-flags` com `--server-side`. A segunda passou a falhar com
`Apply failed with 1 conflict`. Alguém sugere adicionar `--force-conflicts` "para destravar".

## Contexto

Projeto `ac12-declarativo`.

## Como reproduzir com segurança

```bash
oc create configmap ac12-flags --from-literal=cache=on --from-literal=log=info --dry-run=client -o yaml \
  | oc apply --server-side --field-manager=pipeline-a -f - -n ac12-declarativo
oc create configmap ac12-flags --from-literal=log=debug --dry-run=client -o yaml \
  | oc apply --server-side --field-manager=pipeline-b -f - -n ac12-declarativo
```

## Hipóteses a testar

1. `pipeline-b` tenta mudar `data.log`, que pertence ao `pipeline-a`.
2. O ConfigMap é imutável.
3. Falta permissão de `patch`.

## Investigação orientada

- a mensagem do conflito (gerenciador e campo)
- `oc get configmap ac12-flags -n ac12-declarativo --show-managed-fields -o json | jq '.metadata.managedFields[] | {manager, campos: (.fieldsV1."f:data" | keys)}'`

## Critério de resolução

Você identifica o dono do campo e propõe uma divisão de responsabilidades em vez de forçar.

## Limpeza

```bash
oc delete configmap ac12-flags -n ac12-declarativo --ignore-not-found
```
