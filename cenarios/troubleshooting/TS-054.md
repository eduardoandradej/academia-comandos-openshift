# TS-054 — Pending por Insufficient cpu com o nó ocioso

- **Trilha:** [17 — Administração de recursos](../../trilhas/17-admin/README.md)
- **Nível:** Intermediário
- **Perfil:** developer
- **Impacto da reprodução:** MUTAÇÃO LOCAL REVERSÍVEL (1 Deployment)
- **Status:** proposto — ainda não reproduzido contra o cluster pelo autor

## Sintoma

Um Deployment pede `requests.cpu: 3` (três CPUs inteiras). O pod fica `Pending` com `0/1 nodes are available:
1 Insufficient cpu`, embora `oc adm top node` mostre o SNO com 30% de uso.

## Contexto

Projeto `ac17-cotas`. Sem quota que barre o pedido (para o cenário, aplique o pod em um projeto com a baseline e veja a recusa da quota primeiro).

## Como reproduzir com segurança

```bash
oc create deployment ac17-guloso --image=registry.access.redhat.com/ubi9/httpd-24:latest -n ac17-cotas --dry-run=client -o yaml \
  | oc set resources --local -f - --requests=cpu=3,memory=64Mi --limits=cpu=3,memory=128Mi -o yaml | oc apply --dry-run=server -n ac17-cotas -f -
```

O `--dry-run=server` mostra a recusa da quota/LimitRange do projeto. Em um projeto sem esses limites (conceitual),
o pod seria criado e ficaria `Pending`.

## Hipóteses a testar

1. O agendador decide por **requests reservados**, não pelo uso real: o alocável já está quase todo reservado.
2. O nó está com pressão de CPU.
3. Seletor de nó errado.

## Investigação orientada

- (admin) `oc describe node | sed -n '/Allocated resources:/,/Events:/p'`
- `oc adm top node`
- `oc describe pod <pod> | sed -n '/Events:/,$p'` (`Insufficient cpu` × `node selector`)

## Critério de resolução

Você mostra a diferença entre reservado e usado e ajusta o pedido ao que a aplicação realmente usa.

## Limpeza

```bash
oc delete deployment ac17-guloso -n ac17-cotas --ignore-not-found
```
