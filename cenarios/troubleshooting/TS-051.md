# TS-051 — A política liberou demais: o OR escondido na lista from

- **Trilha:** [16 — Rede e isolamento](../../trilhas/16-rede/README.md)
- **Nível:** Avançado
- **Perfil:** developer
- **Impacto da reprodução:** MUTAÇÃO LOCAL REVERSÍVEL (NetworkPolicy)
- **Status:** proposto — ainda não reproduzido contra o cluster pelo autor

## Sintoma

A política deveria liberar a loja **só** para o pod `ac16-cliente` do projeto `ac16-vizinho`. Na auditoria, o
`ac16-intruso` (outro pod do mesmo projeto vizinho) também acessa a loja.

## Contexto

Projetos `ac16-rede` e `ac16-vizinho` (NET-002), com a negação de entrada aplicada.

## Como reproduzir com segurança

```bash
oc delete networkpolicy -l academy.openshift.dev/managed-by=academia -n ac16-rede
oc apply -f manifests/networkpolicies/00-negar-entrada.yaml -n ac16-rede
cat <<'EOF' | oc apply -n ac16-rede -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ac16-ts051
  labels:
    academy.openshift.dev/managed-by: academia
spec:
  podSelector: {matchLabels: {app: loja}}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ac16-vizinho
        - podSelector:
            matchLabels:
              app: ac16-cliente
EOF
oc exec ac16-intruso -n ac16-vizinho -- timeout 3 bash -c '</dev/tcp/web-azul.ac16-rede.svc/8080' && echo "intruso entrou"
```

## Hipóteses a testar

1. `namespaceSelector` e `podSelector` estão em itens separados: OR.
2. Existe outra política mais permissiva no projeto.
3. O `ac16-intruso` tem o rótulo `app=ac16-cliente`.

## Investigação orientada

- `oc get networkpolicy ac16-ts051 -n ac16-rede -o jsonpath='{.spec.ingress[0].from}' | jq .`
- `oc get networkpolicy -n ac16-rede`
- `oc get pod ac16-intruso -n ac16-vizinho --show-labels`

## Critério de resolução

Você aponta o hífen que transformou a regra em OR e corrige para AND.

## Limpeza

```bash
oc delete networkpolicy -l academy.openshift.dev/managed-by=academia -n ac16-rede
```
